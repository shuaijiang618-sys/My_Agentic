## 1. 面试如何介绍本项目

### 30 秒版（开场）

> 我做的是一个**医疗导诊与报告解释助手**，面向医院/互联网医疗场景，帮助用户理解症状、检查指标（如 ALT、血糖），并建议可能就诊科室。  
> 技术上它是 **FastAPI + Multi-Agent + RAG + 多层安全门禁** 的 LLM 应用，支持多租户知识库、JWT 鉴权、Prometheus 可观测和自动化回归测试。  
> 我重点解决的不是「让模型多说」，而是**医疗场景下怎么答得准、答得安全、答得有依据**。

### 1～2 分钟版（展开）

**背景与定位**

- 用户常见两类问题：「该挂什么科？」「体检指标什么意思？」
- 产品边界清晰：**只做辅助解释和导诊建议**，不做确诊、不开方；急症走 120 模板
- 这是 **POC / 工程化原型**，不是医疗器械；面试里要主动讲合规边界

**核心链路**

```
鉴权 → 输入安全预检 → RAG 检索 + 知识门禁 → Multi-Agent 生成 → Safety Judge → 免责声明
```

**技术亮点（面试官常追问）**

| 模块 | 要点 |
|------|------|
| 三层安全 | 输入预检 + RAG Evidence-first 门禁 + Safety Judge 输出后检 |
| Multi-Agent | Intent → Triage / Report / General / Emergency 路由 |
| RAG 工程 | ChromaDB 多租户、查询改写/重排、RAG 预检降本、返回 sources[] |
| 鉴权多租户 | API Key / JWT（Keycloak）、`{tenant}:{user_id}` 记忆分桶 |
| 可观测 | runs.jsonl 审计、Prometheus KPI、安全/鉴权自动化回归 |

**STAR 故事示例**

- **Evidence-first**：用户问 ALT 偏高 → 检索 Top-1 < 0.4 拒答；补知识库 + 租户回填 → 命中 ALT.md，score ~0.51，带 sources 可追溯回答
- **鉴权联调**：AUTH_ENABLED 开启后前端 401/403 → JWT 自动同步 sub/tenant_id → doctor 用户正常对话

**务必主动说的边界**

- 辅助信息工具，非诊断、非处方
- POC 非医疗器械，上线需隐私政策、日志脱敏、人工复核、监管评估
- 身份鉴权（谁能调 API）与业务门禁（能不能答）是两套机制

**一句话收尾**

> 这个项目把 LLM 应用从 Demo 做到可测、可管、可上线：**Agent 编排 + RAG 有据 + 医疗安全门禁 + 多租户鉴权 + 全链路观测**。

## 3. 多租户知识库、JWT 鉴权、Prometheus 可观测与自动化回归

### 总览

四个能力在架构上**分层解耦**：

```
JWT/API Key 鉴权（谁在调用、属于哪个租户）
        ↓
多租户 RAG（只能检索 shared + 本租户知识）
        ↓
/chat 主链路（Agent + 安全门禁）
        ↓
Prometheus 指标 + JSONL 审计 + 自动化回归脚本
```

---

### 3.1 多租户知识库

#### 设计思路

每个知识片段在 ChromaDB metadata 里带 `tenant_id`：

- **`shared`**：所有租户可见（公共科普、通用检查项说明）
- **`hospital_a` 等**：租户私有库

检索 filter：**本租户 OR shared**，既隔离又共享公共知识。

#### 核心实现

**1. ACL 过滤逻辑**（`core/knowledge_acl.py`）

```python
# 租户可见：tenant_id = 当前租户 OR shared
{"$or": [{"tenant_id": tenant_id}, {"tenant_id": "shared"}]}
```

**2. 写入时打标**（`mcp/knowledge_base.py`）

- `add_documents(..., tenant_id="shared")`：每个 chunk metadata 写入 `tenant_id`
- `import_from_directory(..., tenant_id=auth.tenant_id)`：批量导入时按调用方租户打标
- admin 通过 `X-Tenant-ID` 指定目标租户导入

**3. 检索时过滤**（`knowledge_base.search`）

- Chroma `where` 传入 `build_tenant_where(tenant_id)`
- 结果二次校验 `meta_tenant in {tenant_id, "shared"}`

**4. 主链路接入**（`api/main.py`）

`/chat` 从 `auth.tenant_id` 取租户，传给 `_build_knowledge_context(message, tenant_id=auth.tenant_id)`。

**5. 历史数据回填**

旧片段无 `tenant_id` 时多租户 filter 查不到。`backfill_tenant_shared()` 补打 `shared`，再配合 `--tenant hospital_a` 导入租户私有文档。

#### 记忆分桶（与知识库配套）

鉴权开启后，Redis/Chroma 记忆 key 用 `{tenant_id}:{user_id}`，避免跨租户 user_id 碰撞（`AuthContext.effective_user_id`）。

---

### 3.2 JWT 鉴权

#### 设计思路

网关式 Bearer Token，**两套凭证并存**：

| 类型 | 场景 |
|------|------|
| **API Key** | 内测脚本、简单集成 |
| **JWT/OIDC** | Keycloak 联调、生产 IdP |

默认 `AUTH_ENABLED=false`，POC 免登录；内测设 `true` 后各接口 Depends 校验。

#### 两层「权限」

| 类型 | 控制什么 | 模块 |
|------|----------|------|
| **身份/接口** | 谁调用、能否调管理 API、看哪份 KB | `core/auth.py`、`core/jwt_auth.py` |
| **业务/内容** | 能否回答、有无 RAG 依据 | `core/medical_security.py` |

鉴权在业务门禁**之前**执行，两者不混淆。

#### JWT 校验流程

**1. 入口**（FastAPI Depends）

| Depends | 接口 | 最低角色 |
|---------|------|----------|
| `require_chat_auth` | `/chat`、`/search` | chat |
| `require_readonly_auth` | `/knowledge/stats`、`/monitor` | readonly |
| `require_admin_auth` | `/knowledge/add`、`/import`、`/prompts/reload` | admin |

**2. Token 解析**（`verify_bearer_token`）

```
Bearer Token
  → 形如 JWT（两个点）且 AUTH_JWT_ENABLED → verify_jwt_token
  → 否则 → verify_api_key
  → 返回 AuthContext(role, tenant_id, user_id, auth_source)
```

**3. JWT 校验**（`core/jwt_auth.py`）

- **RS256 + JWKS**：Keycloak `AUTH_JWT_JWKS_URL` 拉公钥验签
- **HS256**：内测 `AUTH_JWT_SECRET` + `scripts/gen_test_jwt.py`
- Claims 映射：
  - `sub` → `user_id`
  - `tenant_id`（支持 Keycloak 数组 claim）→ 租户
  - `realm_access.roles` + `AUTH_JWT_ROLE_MAP` → chat/readonly/admin

Keycloak 配置示例：

```bash
AUTH_JWT_ISSUER=http://localhost:8080/realms/medical
AUTH_JWT_JWKS_URL=.../protocol/openid-connect/certs
AUTH_JWT_ROLE_MAP=md-chat:chat,md-admin:admin,md-readonly:readonly
```

**4. user_id 防伪造**（`validate_client_user_id`）

JWT 的 `sub` 与请求体 `user_id` 必须一致（或客户端传 `anonymous`）；否则 403。前端从 JWT 自动同步 `sub`，避免与默认 `u1001` 冲突。

**5. admin 跨租户操作**

admin 且 `tenant_id=*` 时，可通过 Header `X-Tenant-ID` 指定导入/管理的目标租户。

#### 与 Keycloak 联调

```bash
./scripts/keycloak_up.sh                              # Docker 起 Keycloak + realm 导入
./scripts/keycloak_token.sh doctor doctor123          # 取 JWT
./scripts/keycloak_smoke.sh                           # Token + /chat 端到端
```

测试账号：`doctor`（chat）、`kbadmin`（admin）、`viewer`（readonly）。

### 3.3 Prometheus 可观测

#### 三层观测

| 层 | 实现 | 用途 |
|----|------|------|
| **请求级 Counter/Histogram** | `monitor/metrics.py` | 实时指标 |
| **JSONL 审计** | `observability.py` → `logs/runs.jsonl` | 单次请求追溯 |
| **Prometheus 预聚合 + 告警** | `prometheus/recording_rules/`、`alerts/` | 大盘与告警 |

#### 指标写入点

`/chat` 各分支调用 `record_chat_*`：

| 函数 | 时机 |
|------|------|
| `record_chat_blocked` | 输入 / RAG / Agent 阶段拦截 |
| `record_chat_success` | 正常完成 |
| `record_chat_llm_failed` | Agent LLM 失败 |
| `record_chat_error` | 未预期异常 |
| `record_chat_business_kpis` | RAG 命中、有效回答、HITL |

#### 关键指标

**安全与链路：**

- `medical_chat_requests_total{outcome}` — success / blocked_input / blocked_rag / llm_failed …
- `medical_knowledge_gate_blocks_total{reason}` — RAG 门禁拦截
- `medical_safety_judge_blocks_total` — 输出后检拦截
- `medical_chat_latency_seconds` — 延迟分布

**成本：**

- `medical_llm_tokens_total{stage, kind}` — 各 stage prompt/completion token
- `medical_llm_errors_total{stage, reason}` — timeout / 429 / 5xx
- `medical_llm_retries_total` — 重试次数

**业务 KPI（原始 Counter，比率由 recording rules 计算）：**

- `medical_chat_rag_queries_total` / `medical_chat_rag_hits_total` → **RAG 命中率**
- `medical_chat_effective_answers_total` → **有效回答率**
- `medical_chat_hitl_total` → **人工转接率**

预聚合示例（`prometheus/recording_rules/medical-kpi.yml`）：

```yaml
medical:rag_hit_rate:5m = rate(rag_hits) / rate(rag_queries)
medical:effective_answer_rate:5m = rate(effective_answers) / rate(chat_requests)
medical:llm_failure_rate:5m = rate(llm_errors) / rate(llm_attempts)
```

#### 暴露与使用

- 应用内：`GET /metrics`（FastAPI mount `prometheus_client` ASGI app）
- 可选：`./scripts/start_prometheus.sh` 起 Docker Prometheus + Alertmanager
- `/health` 的 `audit` 字段汇总近 500 条 JSONL 的 KPI 比率

#### JSONL 审计（补充 Prometheus）

每条 `/chat` 写 `runs.jsonl`：`request_id`、`intent`、`sources`、`blocked`、`latency_ms`、`tokens`、`llm_errors` 等，支持事后排查与 badcase 挖掘。

### 3.4 自动化回归测试

#### 设计思路

按**是否需要 LLM / 是否需起服务**分套件，改 Prompt/规则/鉴权后一键回归。

| 脚本 | 套件 | 依赖 | 说明 |
|------|------|------|------|
| `./scripts/run_safety_checks.sh` | 安全规则 | 无 LLM、无服务 | ~15 条 |
| `./scripts/run_auth_checks.sh` | 鉴权模块 | 无 LLM、无服务 | ~9 条 |
| `./scripts/run_retrieval_eval.sh` | RAG 阈值 | 需 Chroma + embedding | 检索 case |
| `./scripts/run_chat_eval.sh` | 端到端 Chat | 需 API + LLM Key | 采样 case |

#### 1. 安全回归（`evaluation/safety_runner.py`）

纯规则层，**不调 LLM**：

- 输入拦截：开方、确诊、敏感词、紧急症状
- RAG 门禁：无检索 / 低分拒答
- Safety Judge 规则：确诊表述、剂量建议、敏感输出
- 空 Agent 响应拒答

```bash
./scripts/run_safety_checks.sh
# 或 HTTP: GET /eval/safety
```

#### 2. 鉴权回归（`evaluation/auth_runner.py`）

纯单元测试，**无需启动 8010**：

- API Key 解析与校验
- `effective_user_id` 租户前缀
- `build_tenant_where` 含 shared
- JWT HS256 签发/校验 roundtrip
- Keycloak `tenant_id` 数组 claim

```bash
./scripts/run_auth_checks.sh
```

#### 3. RAG 检索评测（`evaluation/retrieval_threshold_runner.py`）

用 `retrieval_cases.json` 标定 `MIN_RETRIEVAL_SCORE`（当前 0.4），测 Recall/MRR 等。

#### 4. 端到端 Chat 采样（`evaluation/chat_sample_runner.py`）

批量调 `/chat`，输出 Markdown/JSON 报告供人工评分；Prompt E2E 另有 `prompt_e2e_runner.py`。

#### 回归在 CI 中的价值

```
改 medical_security 规则  → run_safety_checks
改 auth/jwt              → run_auth_checks
改 RAG 阈值/embedding    → run_retrieval_eval
改 Prompt/Agent          → run_chat_eval + 人工看 badcase
```

P0 安全 case 必须 100% 通过才能认为可上线内测。

### 3.5 四者串联（一次 `/chat` 请求）

```
1. Authorization: Bearer <JWT>
   → jwt_auth 验签 → AuthContext(tenant=hospital_a, role=chat, user=sub)

2. validate_client_user_id + effective_user_id → hospital_a:uuid

3. RAG search(tenant_id=hospital_a)
   → Chroma where: hospital_a OR shared
   → Top-1 score ≥ 0.4 才继续

4. Agent 生成 → Safety Judge → disclaimer

5. record_chat_success + runs.jsonl + Prometheus counters

6. 若改动了规则/鉴权 → run_safety_checks + run_auth_checks 验证
```

**面试一句话：**

> 多租户是 Chroma metadata + `$or` filter 实现 shared/私有隔离；JWT 是 FastAPI Depends + JWKS 验签 + 角色/tenant claims 映射；可观测是 Prometheus 业务 KPI + JSONL 全链路审计；回归是把安全/鉴权/RAG/Chat 拆成无需 LLM 的脚本套件，保证改代码不翻车。

## 4. 如何做到答得准、答得安全、答得有依据

### 一句话

用**固定顺序的主链路**，把「准、安全、有据」拆成三道可审计的门禁，而不是只靠 Prompt 写「请谨慎回答」：

```
鉴权 → 输入预检 → RAG + 知识门禁 → 专用 Agent → Safety Judge → 免责声明
```

---

### 4.1 答得「有依据」—— Evidence-first RAG

**核心原则：需要知识支撑的问题，没有合格检索就不让 Agent 编。**

#### 1. 判断哪些问题「必须有依据」

`_requires_knowledge_evidence()`（`api/main.py`）根据关键词（症状、挂科、ALT、血糖、体检等）判断；寒暄「你好」不要求知识库。

#### 2. 多租户 RAG 检索

- ChromaDB 按 `tenant_id` 过滤：可见 **本租户 + shared 公共库**
- 检索链路：向量召回 →（可选）查询改写 → 重排
- **RAG 预检**：全量改写/重排前先 Top-1 预检，低分直接跳过，省成本且避免无意义生成

#### 3. 知识门禁（`check_knowledge_gate`）

| 条件 | 结果 |
|------|------|
| 不需要依据（寒暄等） | 放行 |
| 需要依据但 `source_count=0` | **拒答**（no_retrieval） |
| Top-1 score < **0.4**（`MIN_RETRIEVAL_SCORE`） | **拒答**（low_retrieval） |
| score ≥ 0.4 | 放行，把知识片段拼进 Agent context |

阈值 0.4 用 `run_retrieval_eval.sh` 离线标定，不是拍脑袋。

#### 4. 可追溯

- `/chat` 返回 `sources[]`（标题、内容、score、doc_type）
- `logs/runs.jsonl` 审计每条请求的检索与 outcome

**面试话术：**

> 不是「先让模型答，再希望它别胡编」，而是「检索不过关就不调用 Agent」—— Evidence-first，比事后免责声明更硬。

---

### 4.2 答得「安全」—— 三层防护 + fail-closed

#### 第 1 层：输入预检（`check_question` / `check_question_async`）

在 RAG 和 Agent **之前**拦截（`core/medical_security.py`）：

| 类型 | 处理方式 |
|------|----------|
| 紧急症状（胸痛、昏迷、自杀等） | 固定 **120/急诊模板**，不进入普通 Agent |
| 高危意图（确诊、开方、剂量、推荐药物） | 直接拒答 |
| 偏题（写代码、股票、笑话） | 拒答 |
| 敏感词 / 可选内容安全 API | 拒答 |
| 可选偏题 LLM 分类 | 二次拦截 |

#### 第 2 层：RAG 门禁

无依据 / 低分 → 不调 Agent，从根上防幻觉。

#### 第 3 层：输出后检（`SafetyJudge`）

Agent 生成完整回答后再检（`core/safety_judge.py`）：

- **规则**：确诊表述（「你就是 XX 病」）、处方/剂量、敏感输出
- **可选 LLM Judge**：JSON 判定 safe/unsafe，可安全改写
- **fail-closed**：Judge LLM 失败时**降级为仅规则**；规则仍拦越权/敏感

**其他安全兜底：**

- Agent 返回空/过短 → `check_empty_agent_response` 强制拒答
- 每条正常回复强制附加 **免责声明**（`append_disclaimer`）

**两层权限要分清（面试加分）：**

| 类型 | 控制什么 |
|------|----------|
| **身份鉴权**（JWT/API Key） | 谁能调接口 |
| **业务门禁**（medical_security） | 能不能答、怎么答 |

---

### 4.3 答得「准」—— 专 Agent + 结构化 + Skills

「准」指 **意图对、场景对、格式对**，不是「替医生下诊断」。

#### 1. Intent 识别 → 专用 Agent 路由

`IntentRecognizer` 识别导诊 / 报告解释 / 紧急 / 寒暄 / 泛医学，路由到不同 Agent（`agents/agent_orchestrator.py`）：

| Agent | 职责 |
|-------|------|
| TriageAgent | 症状 → 可能科室 |
| ReportInterpretationAgent | ALT、血糖等指标解释 |
| GeneralMedicalAgent | 泛医学科普 |
| EmergencyAgent | 紧急模板 |
| GreetingAgent | 寒暄 |

各 Agent 有**独立 system prompt**（`prompts/agents/`），禁止确诊/开方写在规则里。

#### 2. RAG 上下文注入

检索通过后，知识片段 + 会话记忆拼进 `full_context`，Agent **基于片段生成**，而不是纯靠模型参数记忆。

#### 3. 结构化输出（triage/report/general）

- `prompts/output_schemas.yaml` 定义 JSON 字段
- `core/structured_response.py` 解析、校验、渲染成固定段落
- 解析失败 **自动重试 1 次**，仍失败回退原文

保证导诊/报告类回答结构稳定（如「指标含义 → 常见原因 → 建议就医」）。

#### 4. Skills 注入

`skills/*/SKILL.md` 按关键词和 `user_id` 分桶注入（如 ALT 问题命中「报告解释规范」「医疗安全边界」），强化领域话术与安全边界一致。

#### 5. 记忆

Redis + Chroma 三级记忆，鉴权开启时 `{tenant}:{user_id}` 分桶，多轮对话有上下文但不跨租户串数据。

---

### 4.4 主链路示例（「ALT 52 偏高什么意思」）

```
1. JWT 鉴权 → tenant=hospital_a
2. 输入预检 → 正常医疗问题，放行
3. RAG 检索（hospital_a + shared）→ 命中 lab_item/ALT.md，score≈0.51
4. 知识门禁 → score ≥ 0.4，放行
5. Intent=report → ReportAgent + RAG context + Skills
6. 结构化生成回答
7. Safety Judge → 无确诊/开方，通过
8. 附加 disclaimer，返回 response + sources[]
9. 写 runs.jsonl + Prometheus 指标
```

若 score=0.2 → 第 4 步拒答，**Agent 不会被调用**。

---

### 4.5 怎么证明「真的有效」？

| 维度 | 手段 |
|------|------|
| 安全 | `run_safety_checks.sh` ~15 条规则回归 |
| 鉴权 | `run_auth_checks.sh` ~9 条 |
| 检索 | `run_retrieval_eval.sh` 标定 0.4 阈值 |
| 线上 | Prometheus：RAG 命中率、门禁拦截率、Judge 拦截率 |
| 审计 | `logs/runs.jsonl` 逐请求追溯 |
| 迭代 | Badcase 库 + 端到端 Chat 采样 |

### 4.6 面试 30 秒版

> **有依据**：Evidence-first，Top-1 不够 0.4 不调 Agent，返回 sources。  
> **安全**：输入规则 + RAG 门禁 + Safety Judge 三层，紧急走 120 模板，每条带 disclaimer。  
> **准**：Intent 路由专用 Agent，RAG 注入 + Skills + 结构化输出，明确不做确诊开方。

## 5. RAG 检索评测详解

### 5.1 定位

这套评测**不是**测「生成答案写得好不好」，而是专门标定 **Evidence-first 知识门禁**用的 **Top-1 相似度阈值**（`MIN_RETRIEVAL_SCORE`，当前 **0.4**）。

线上逻辑（`api/main.py` + `core/medical_security.py`）：

```
需要依据的问题
  → RAG 检索（向量 / 改写+重排）
  → 取 Top-1 score
  → score < 0.4 → check_knowledge_gate 拒答，不调 Agent
  → score ≥ 0.4 → 放行，知识片段进 Prompt
```

评测要回答：**0.4 这个门槛是否合理？调高调低会怎样？**

---

### 5.2 文件与入口

| 文件 | 作用 |
|------|------|
| `evaluation/retrieval_cases.json` | 评测用例（11 条） |
| `evaluation/retrieval_cases.py` | 加载用例、`RetrievalEvalCase` 数据结构 |
| `evaluation/retrieval_threshold_runner.py` | 核心逻辑：逐条检索、阈值扫描、推荐 |
| `scripts/eval_retrieval_threshold.py` | CLI 入口 |
| `scripts/run_retrieval_eval.sh` | 一键运行 |

```bash
cd "AI-Powered Medical Diagnostics"
./scripts/run_retrieval_eval.sh                    # 默认 direct 模式
./scripts/run_retrieval_eval.sh --mode rewrite     # 与线上一致的改写+重排
./scripts/run_retrieval_eval.sh --json             # 仅 JSON 报告
```

---

### 5.3 评测用例设计

每条 case 四个字段：

```json
{
  "name": "alt_high",
  "query": "ALT 52 偏高是什么意思",
  "should_answer": true,
  "note": "lab_item"
}
```

| 字段 | 含义 |
|------|------|
| `query` | 用户问题 |
| `should_answer` | **期望门禁放行**（true）还是**期望拒答**（false） |
| `note` | 文档类型或说明 |

#### 正例（5 条，`should_answer=true`）

知识库**应有**足够相关片段，期望 Top-1 ≥ 阈值：

| name | query | 覆盖类型 |
|------|-------|----------|
| alt_high | ALT 52 偏高是什么意思 | lab_item |
| triage_abdominal | 肚子胀恶心应该挂什么科 | department |
| blood_pressure | 血压偏高要注意什么 | popular_science |
| registration_flow | 门诊挂号流程是怎样的 | hospital_flow |
| respiratory_triage | 咳嗽胸闷看什么科 | department |

#### 负例（6 条，`should_answer=false`）

期望 **Top-1 低于阈值或无命中**，门禁应拦：

| name | query | 原因 |
|------|-------|------|
| oob_crp / oob_psa | CRP/PSA 指标 | **库外题**，默认库无文档 |
| off_topic_stock / off_topic_code | 股票、写代码 | 非医疗 |
| vague_short | 嗯 | 过短无意义 |
| wrong_domain | 王者荣耀怎么上分 | 非医疗 |

正负例一起用，才能同时衡量「该答的别误拒」和「不该答的别误放」。

---

### 5.4 两种检索模式

#### `direct`（默认）

- 仅 **Chroma 向量检索**（`kb.search`）
- **不需要 LLM API Key**
- 速度快，适合 CI、改 embedding/知识库后快速回归

#### `rewrite`

- 走线上同款 **`search_with_rewrite`**（查询改写 + 重排）
- **需要** `DEEPSEEK_API_KEY` 或 `ANTHROPIC_API_KEY`
- 与生产链路一致，但慢、有成本

```bash
./scripts/run_retrieval_eval.sh --mode direct --top-k 3
./scripts/run_retrieval_eval.sh --mode rewrite --top-k 3
```

> 线上还有 **RAG 预检**（先 direct Top-1，不够 0.4 就不跑 rewrite）。`direct` 评测纯向量；`rewrite` 评测全链路检索后 Top-1。

---

### 5.5 评测流程（核心算法）

#### Step 1：逐条检索（`evaluate_queries`）

对每个 case 调用 `search_fn(query)`，记录：

- `top_score`：所有 hit 里**最高分**（等价 Top-1）
- `top_title`：对应文档标题
- `hit_count`：返回条数

分数来自 Chroma 距离换算：`score = 1.0 - distance`（`knowledge_base.search`）。

#### Step 2：阈值扫描（`sweep_thresholds`）

在 **0.30～0.55，步长 0.05** 上模拟门禁：

```
gate_pass = (top_score >= threshold)
```

对每个阈值计算：

| 指标 | 定义 | 医疗含义 |
|------|------|----------|
| **误拒答率**（false_reject_rate） | 应答题中 score < 阈值 的比例 | 库里有依据却被拦 |
| **误放行率**（false_accept_rate） | 应拒题中 score ≥ 阈值 的比例 | 库外/无关题却放行，可能幻觉 |
| **召回 recall_pass** | 应答题中被放行的比例 | 覆盖率 |
| **精确 precision_pass** | 放行样本里应答题占比 | 放行质量 |

#### Step 3：推荐阈值（`recommend_threshold`）

策略：**误放行优先**（医疗更安全）

1. 先筛 `false_accept_rate ≤ max_false_accept`（默认 **0%**）
2. 在可行阈值里选 **误拒答率最低** 的
3. 若仍 tie，取**更高阈值**（更严）

若无阈值能满足 0 误放行，取扫描范围内**最严**阈值并给出 reason。

#### Step 4：分数分布（`score_distribution`）

分别统计 `should_answer` / `should_reject` 的 min、p10、median、p90、max，便于肉眼看正负例是否可分。

---

### 5.6 输出报告解读

#### Top-1 分数分布

```
should_answer: n=5  median=0.51  p10=0.42  p90=0.58
should_reject: n=6  median=0.22  p10=0.10  p90=0.35
```

理想情况：**正例 median 明显高于负例**，阈值 0.4 落在中间空隙。

#### 逐条检索

```
[应答] alt_high            score=  0.5100  title=ALT
[应拒] oob_crp             score=  0.1800  title=...
```

#### 阈值扫描表

```
  阈值    误拒答率    误放行率      召回      精确
  0.30      0.0%       33.3%     100.0%     60.0%
  0.40      0.0%        0.0%     100.0%    100.0%  ← 当前
  0.45      20.0%       0.0%      80.0%    100.0%
```

### 5.7 与线上主链路的对应

```
                    评测测的是这里 ──────────────┐
                                                 ▼
用户问题 → RAG 检索 → Top-1 score ──→ check_knowledge_gate
              │              │
              │              └── MIN_RETRIEVAL_SCORE (0.4)
              │
              ├── RAG 预检：direct Top-1 < 0.4 → 跳过 rewrite（省钱）
              └── RAG_LITE：direct 检索 + 同一阈值
```

`MIN_RETRIEVAL_SCORE` 定义在 `core/medical_security.py`，被以下共用：

- `check_retrieval_score` / `check_knowledge_gate`（最终门禁）
- `_build_knowledge_context` 预检与 RAG_LITE
- `eval_retrieval_threshold.py` 标定

**改阈值必须跑评测**，不能凭感觉调。

### 5.8 使用前提与常见问题

#### 运行前

1. 知识库已导入：`./scripts/import_knowledge.sh`
2. Chroma 可访问（本地 `./data/chroma` 或 `CHROMA_HOST/PORT`）
3. 多租户：case 默认无 tenant；需确保 `ALT.md` 等在 `shared` 或对应 tenant 可见

#### 典型踩坑

| 现象 | 原因 | 处理 |
|------|------|------|
| 正例 score 很低 | 库未导入 / 无 `tenant_id` | import + backfill |
| 负例 score 很高 | 库里有弱相关噪音 | 加负例、调 embedding 或提高阈值 |
| direct 与 rewrite 差很多 | 改写/重排显著改变排序 | 用 `--mode rewrite` 标定线上阈值 |
| 误拒答高 | 阈值过高 | 在 0 误放行下选更低阈值或补知识库 |


建议新增：各 `doc_type` 正例、库外指标、易混淆近义问法。

| 评测 | 测什么 | 与 RAG 检索评测关系 |
|------|--------|---------------------|

| **run_safety_checks** | 规则层（含 gate 逻辑） | 不测真实检索分数 |
| **run_chat_eval** | 端到端 `/chat` | 含 Agent+Judge，成本高 |
| **MRR/nDCG** | 排序质量 | 可扩展 MRR@K，当前用门禁二分类 |

### 5.10 面试 30 秒版

## 6. RAG 评测准确性与防幻觉方案

### 6.1 核心思路

医疗 RAG 的幻觉，本质是 **没有可靠依据仍生成像真的医学结论**。  
本项目不靠 Prompt「请谨慎回答」，而是用 **检索过关才生成 + 多层兜底**：

```
提升检索质量（少漏召、少误召）
    → 检索不过关就不调 Agent（Evidence-first）
        → Prompt 约束「仅依据片段」
            → 输出后 Safety Judge 再检
                → 离线检索评测 + 安全回归持续标定
```

---

### 6.2 幻觉类型与拦截点

| 幻觉类型 | 例子 | 拦截点 |
|----------|------|--------|
| **无依据编造** | 库里没有 CRP，仍解释 CRP 180 | RAG 门禁 + 检索评测负例 |
| **弱相关硬答** | 检索 score 很低仍生成 | Top-1 < 0.4 拒答 |
| **越权结论** | 「你就是 XX 病」「每天吃 2 片 XX」 | 输入预检 + Safety Judge |
| **片段外发挥** | 有 ALT 片段却编造具体治疗方案 | Prompt 规则 + Judge |

| 评测 | 作用 |
|------|------|
| **检索评测** | 管「该不该放行」 |
| **安全回归** | 管「放行/拒答逻辑是否正确」 |
| **Chat 采样** | 管端到端是否仍胡编 |

---

### 6.3 检索准确性：该找到的找到、不该放的拦住

#### 检索链路

```
用户 query → 向量召回（ChromaDB）
          → 查询改写（rewrite，扩 3 条子 query）
          → 合并去重 → LLM 重排（rerank）
          → Top-K / Top-1 score
```

- **改写 + 重排**：缓解口语问法与文档表述不一致
- **多租户 filter**：`tenant_id = 本租户 OR shared`，减少跨租户噪音
- **RAG 预检**（默认）：rewrite/rerank 前先 direct Top-1；< 0.4 跳过改写/重排，避免低分被后续步骤误抬高

#### Evidence-first 门禁（防幻觉核心闸门）

主链路顺序（`api/main.py`）不可打乱：

```
check_question_async → _build_knowledge_context → check_knowledge_gate → Agent → SafetyJudge
```

`check_knowledge_gate`（`core/medical_security.py`）：

| 条件 | 行为 |
|------|------|
| 不需要依据（寒暄等） | 放行 |
| 需要依据但 `source_count=0` | **拒答**（no_retrieval） |
| Top-1 score < **0.4** | **拒答**（low_retrieval） |
| score ≥ 0.4 | 放行，片段注入 Prompt |

**检索不过关时 Agent 不会被调用**，架构上切断「凭空编医学解释」。

拒答文案：`prompts/security/block_no_evidence.md`——明确「无足够匹配，无法给出具体医学说明」，引导线下就医。

#### 阈值标定（见第 5 章）

`retrieval_cases.json` 5 正 6 负 + 阈值扫描，**0 误放行优先**。改 embedding/知识库/rewrite 后须重跑 `run_retrieval_eval.sh`。

---

### 6.4 生成阶段：约束「只依据片段说」

#### Prompt 层

- `prompts/shared/system_rules.txt`：优先依据片段；证据不足不编造
- `prompts/rag/context.yaml`：检索结果标为「不可信数据区」，仅依据相关片段，不得补充库外结论
- `prompts/shared/injection_guard.txt`：防注入覆盖规则
- `prompts/shared/few_shot.txt`：含「无匹配拒答」范例

#### 结构化输出

`output_schemas.yaml` + `structured_response.py`：固定字段（如 `data_note` 标注是否依据检索）；解析失败重试 1 次。

#### 专用 Agent + Skills

Report / Triage 等分 Agent；ALT 等问题注入「报告解释规范」「医疗安全边界」Skills。

---

### 6.5 生成后：Safety Judge

| 层级 | 内容 |
|------|------|
| **规则** | 确诊表述、处方/剂量、敏感输出 |
| **可选 LLM Judge** | JSON 判定 safe/unsafe，可安全改写 |
| **fail-closed** | Judge LLM 失败 → 仅规则仍拦截 |

`check_empty_agent_response`：空/过短 Agent 正文 → 强制拒答。

---

### 6.6 全链路示例

**库外题「CRP 180 严重吗」（负例 oob_crp）：**

```
输入预检放行 → RAG Top-1 低 → check_knowledge_gate 拒答
→ Agent 不调用 → block_no_evidence → blocked=true → 记 blocked_rag
```

**「ALT 52 偏高」（正例 alt_high）：**

```
RAG 命中 ALT.md score≈0.51 → 门禁放行 → ReportAgent 基于片段
→ Judge 通过 → disclaimer → response + sources[]
```

---

### 6.7 可观测与持续验证

| 手段 | 防什么 |
|------|--------|
| `run_retrieval_eval.sh` | 阈值与检索能力脱节 |
| `run_safety_checks.sh` | 门禁规则被改坏 |
| `run_chat_eval.sh` | 端到端仍胡编 |
| `medical_knowledge_gate_blocks_total` | 线上 RAG 拦截异常 |
| `medical_chat_rag_hits_total` / queries | 命中率下降 |
| `logs/runs.jsonl` | 单条追溯 sources、score、blocked |

**Badcase 闭环**：翻车 case → 加入 `retrieval_cases.json` 或安全用例 → 回归通过再发版。

---

### 6.8 方案分层（面试用）

```
L0 检索评测     标定 MIN_RETRIEVAL_SCORE，0 误放行优先
L1 检索增强     改写 + 重排 + 多租户 + 预检
L2 Evidence-first  无/弱检索 → 不调 Agent，固定拒答
L3 Prompt/Skills  仅依据片段、few-shot 拒答、防注入
L4 Safety Judge   确诊/开方/敏感输出后检
L5 审计/KPI       sources[]、JSONL、Prometheus
```

**一句话：**

> **检索评测**保证门禁阈值准；**Evidence-first**保证没依据不生成；**Prompt + Judge**保证生成了也不越界；**sources + 审计**保证可追责、可迭代。

---

### 6.9 已知边界

- Top-1 相似度 ≠ 事实正确；高 score 仍可能片段不完全匹配 → Judge + 人工抽检
- 评测 11 条为 POC 规模，生产需扩 case
- 线上标定宜用 `--mode rewrite`，与 direct 分数可能不同
- Prompt 约束不能替代程序门禁（`system_rules.txt`：程序层优先）

---

### 6.10 面试 30 秒版

> 防幻觉靠 **Evidence-first**：检索 Top-1 不够 0.4 不调 Agent；检索评测用 5 正 6 负标定阈值、0 误放行优先；生成侧 Prompt 限定仅依据片段，输出后 Safety Judge 拦确诊开方；全链路 sources + JSONL 可追溯。不是让模型少说，是从架构上 **没依据就不让说**。

## 7. 多轮对话上下文失真解决方案

### 7.1 问题定义

多轮对话中常见的「上下文失真」：

| 失真类型 | 例子 |
|----------|------|
| **话题漂移** | 先问 ALT，再问「挂什么科」，模型仍按指标解释 |
| **陈旧知识** | 第 1 轮 RAG 片段一直带着，第 2 轮新问题仍用旧依据 |
| **窗口爆炸** | 轮数多了 token 爆、中间信息丢失（lost-in-middle） |
| **摘要丢细节** | 压缩后把关键数值、症状压没了 |
| **意图误判** | 短追问「那严重吗」脱离上文被当成新话题 |
| **记忆串线** | 不同用户/会话记忆混在一起 |
| **注入混淆** | 把历史或检索内容当成系统指令 |

---

### 7.2 总体设计

**三级记忆 + 每轮 fresh RAG**，而非把整段聊天历史无节制塞进 LLM。

```
每轮 /chat
  ├─ RAG：按【当前 message】重新检索
  ├─ Memory：按 conv_id 读工作/情景/画像，拼成结构化背景
  ├─ Intent：结合最近 3 轮 history 判意图
  └─ Agent：背景块 +【当前问题】单轮 messages
```

核心文件：`memory/conversation_memory.py`、`api/main.py`。

---

### 7.3 方案 1：会话隔离（防串线）

| 机制 | 实现 |
|------|------|
| **conv_id** | 每次会话独立 ID；Redis key `wm:{user_id}:{conv_id}` |
| **effective_user_id** | 鉴权开启时 `{tenant}:{user_id}`，防跨租户碰撞 |
| **24h TTL** | 工作记忆、摘要自动过期 |
| **前端「新会话」** | 清空 `conversationId`，硬切话题 |

---

### 7.4 方案 2：每轮重新 RAG（防陈旧依据）

每一轮用 **当前 `req.message`** 重新走 `_build_knowledge_context`，**不**复用上一轮 `sources`。

- 每轮独立过 Evidence-first 门禁（Top-1 ≥ 0.4）
- 短追问「那需要挂什么科？」按当前句 + 记忆重新检索，而非绑定第 1 轮 ALT 片段

---

### 7.5 方案 3：三级记忆（控量、分层、按需取）

| 层级 | 存储 | 作用 | 限制 |
|------|------|------|------|
| **L1 工作记忆** | Redis | 当前会话最近消息 | 最大 20 条；≥15 条触发压缩 |
| **L2 情景记忆** | Chroma `episodic` | 压缩后旧对话摘要 | 按当前 query 语义检索 Top-5 |
| **L3 用户画像** | Chroma `user_profile` | symptoms/lab_items 等结构化实体 | 异步 LLM 提炼，非 raw 全文 |

注入 Agent 的格式（`MemoryContext.to_prompt_text`）：

```
[会话摘要]     ← 压缩后的关键信息
[相关历史]     ← 最多 3 条情景检索
[用户画像]     ← 结构化 JSON
[最近对话]     ← 工作记忆原文
```

---

### 7.6 方案 4：工作记忆压缩（防 context 爆炸）

消息 ≥ **15** 条（`COMPRESS_AT`）时：

```
旧消息（除最近 5 条）→ LLM 摘要 2–3 句 → 追加到 Redis summary
                  → 全文存 episodic
工作记忆只保留最近 5 条
```

- 窗口可控，避免 lost-in-middle
- 旧细节可通过情景记忆 + **每轮 fresh RAG** 补回

---

### 7.7 方案 5：背景与当前问题分离

Agent `_call_llm` **不**把全部 history 堆进 `messages`：

```python
# 记忆 + RAG → 不可信背景块
messages.append({"role": "user", "content": background_prefix + context})
messages.append({"role": "assistant", "content": context_ack})
# 当前轮问题单独一条
messages.append({"role": "user", "content": req.message})
```

配合 `prompts/rag/context.yaml`、`injection_guard.txt`：检索与记忆标为 **不可信数据区**，降低旧对话被当成指令/事实的概率。

`full_context = mem_ctx.to_prompt_text() + knowledge_text`（本轮 RAG），记忆与依据分块。

---

### 7.8 方案 6：Intent 多轮消歧

`IntentRecognizer` 仅使用 **history[-3:]**（每条约 80 字）辅助短追问（「严重吗」「挂哪科」）判意图，避免过早历史把意图带偏。

---

### 7.9 方案 7：每轮完整安全链

每一轮仍走：输入预检 → RAG 门禁 → Agent → Safety Judge。上一轮结论不会自动成为下一轮「事实」，防止幻觉滚雪球。

---

### 7.10 全链路示例（两轮）

**第 1 轮**：「ALT 52 偏高什么意思」  
→ RAG 命中 ALT.md → ReportAgent → 工作记忆 + 画像 `lab_items: ["ALT"]`

**第 2 轮**：「那要挂什么科」  
→ `get_context`：recent + 画像  
→ RAG 按**当前句**检索导诊文档  
→ Intent(history[-3:]) → **triage**  
→ TriageAgent：背景 + 本轮 RAG → 挂科建议

---

### 7.11 设计权衡与已知局限

| 已做 | 局限 / 未做 |
|------|-------------|
| 每轮 fresh RAG | 不保证追问必引用同一文档 |
| 压缩 + 摘要 | 极长会话可能丢细粒度数值 |
| 情景记忆 Top-5 | 可能召回弱相关旧话题 |
| Agent 背景块模式 | 依赖 `to_prompt_text()` 质量 |
| conv_id / 新会话 | 不换会话时靠 Intent+RAG 切话题 |

**可增强**：话题切换检测、指代消解（「它」→ ALT）、摘要强制保留 lab 数值、多轮 retrieval case。

---

### 7.12 面试 30 秒版

> 多轮失真用 **conv_id + tenant 前缀隔离**、**每轮按当前问题重新 RAG**、**三级记忆（工作/情景/画像）** 和 **15 条触发压缩留 5 条+摘要**。注入时分块标注不可信数据，Agent 用背景块+当前问题，Intent 只吃最近 3 轮。既不无限堆 history，又避免上一轮检索绑死下一轮。

## 8. 模型答错时的解决方案

### 8.1 先分清：「答错」有哪几类

| 类型 | 例子 | 项目能否自动处理 |
|------|------|------------------|
| **不该答却答了** | 无依据胡编、开方、确诊 | ✅ 强（RAG 门禁 + Judge） |
| **格式/链路错** | JSON 解析失败、Agent 超时 | ✅ 重试 / Fallback |
| **答非所问** | 问挂科却讲指标 | △ Intent 路由 + 每轮 fresh RAG |
| **内容事实错** | 指标解释偏了但语气正常 | ⚠️ POC 主要靠人审 + sources 追溯 |

整体策略：**能程序判定的错 → 拦或改；难判定的错 → 暴露信号 + 人工闭环**，不假装 LLM 自检能覆盖一切。

---

### 8.2 总体架构：预防 → 检测 → 纠正 → 复盘

```
预防少错：Evidence-first + 专 Agent + Prompt/Skills
    ↓
生成中控错：结构化重试、Agent Fallback、LLM 超时重试
    ↓
生成后纠偏：Safety Judge（规则 + 可选改写）
    ↓
仍可能错：sources + hitl_required + 人工评测 + Badcase
```

---

### 8.3 预防层：尽量不让模型「错着答」

#### 1. Evidence-first（防「瞎编式答错」）

需要依据的问题，Top-1 检索 < **0.4**（`MIN_RETRIEVAL_SCORE`）或 0 结果 → **不调 Agent**，直接拒答模板。  
这是对付「答错」的第一道硬闸：没有库就不让编。

#### 2. Intent → 专 Agent（防「答偏题」）

导诊 / 报告 / 泛医学 / 紧急 分路由，避免一个通用 Prompt 什么都答一点。  
Intent 识别用 **最近 3 轮 history**，减轻短追问被当成新话题。

#### 3. Prompt + Skills + 结构化输出（防「格式乱 / 越界表述」）

- `system_rules.txt`：仅依据片段、禁止确诊开方
- Skills 按关键词注入领域规范
- triage/report/general 走 **JSON schema + 模板渲染**，减少自由发挥

#### 4. 每轮 fresh RAG（防「用旧依据答新问题」）

多轮里每轮按**当前 message** 重新检索，避免上一轮文档绑死导致答错轮次（详见 §7）。

---

### 8.4 生成中：链路失败与格式错误的「当场纠正」

#### 1. 结构化输出失败 → 同请求内重试 1 次

`core/structured_response.py` + `agent_*_retry`：

```
首次 JSON 解析/缺字段失败
  → 追加纠正 prompt（build_retry_user_message）
  → 再调一次 LLM
  → 仍失败则回退 raw 文本（并记 Token stage）
```

解决的是 **「答错了格式」**，不是医学事实。

#### 2. Agent 失败 → Fallback General

`agents/agent_orchestrator.py` 中 `_execute`：

```
Triage/Report Agent success=False
  → 自动 Fallback 到 GeneralMedicalAgent
```

避免专 Agent 挂掉后直接空答或 500。

#### 3. LLM 统一超时/重试（`create_message`）

timeout / 429 / 5xx / 网络错误可重试；4xx 不重试。  
失败时 `agent_success=False`，outcome=`llm_failed`，不计入有效回答。

#### 4. 空/过短回复 → 强制拒答

`check_empty_agent_response`：正文过短视为无效，走拒答而非把空内容当成功。

---

### 8.5 生成后：Safety Judge「拦截 + 改写」

模型已经生成，但**答错在安全/合规维度**时：

```
SafetyJudge.judge(question, response)
  1. 规则：确诊表述、处方剂量、敏感词 → passed=False
  2. 可选内容安全 API
  3. 可选 LLM Judge → JSON { safe, reasons, rewrite }
```

**纠正方式**（`api/main.py`）：

| Judge 结果 | 用户看到的 |
|------------|------------|
| `passed=True` | 原回答 + disclaimer |
| `passed=False` 且有 `rewrite` | **Judge 提供的安全改写** + disclaimer |
| `passed=False` 无 rewrite | 固定安全拒答模板（`BLOCK_HIGH_RISK` 等） |

同时：

- `safety_passed=false`
- `hitl_required=true`、`escalated=true` → 提示前端/运营 **需人工关注**
- Prometheus：`medical_safety_judge_blocks_total`、`blocked_judge`

**注意**：Judge LLM 失败会 **降级为仅规则通过**（fail-open on judge，fail-closed on rules）。事实性小错规则拦不住。

---

### 8.6 前端/API 信号：告诉调用方「这答可能不可靠」

`ChatResponse` 暴露多维状态，便于 UI 或下游决策：

| 字段 | 含义 |
|------|------|
| `blocked` | 输入/RAG/Agent 阶段直接拒答 |
| `safety_passed` | Judge 是否通过 |
| `hitl_required` | 建议人工介入（升级 / Judge 未过 / 紧急） |
| `escalated` | 同 HITL 相关升级 |
| `sources[]` | 依据追溯，人可核对是否答错题 |
| `knowledge_used` | 是否用了 RAG |
| `request_id` | 查 `runs.jsonl` 审计 |

**有效回答** KPI 定义很严（`api/main.py`）：

```python
effective = agent_success and safety_passed
hitl = escalated or not safety_passed or emergency
```

只有 **Agent 成功 + Judge 通过** 才算 `effective_answer`；答错被 Judge 拦下不会虚高指标。

---

### 8.7 事实性答错：POC 靠「人 + 数据闭环」

细粒度事实错误（如 ALT 解释略偏）程序很难 100% 判，项目设计是：

#### 1. sources 可追溯

回答带 `sources[]`（title、content、score），医生/运营可对照知识库看是否引错、讲错。

#### 2. 端到端采样 + 人工评审

`scripts/run_chat_eval.sh` + `evaluation/chat_sample_cases.json`：

- 自动断言：`blocked`、`emergency`、`knowledge_used` 等硬指标
- **医学内容是否正确** → 明确写「需人工阅读 full_response 与 sources」

#### 3. 检索 / 安全 / Prompt 回归

| 脚本 | 防什么「答错」 |
|------|----------------|
| `run_retrieval_eval.sh` | 门槛太低 → 胡编；太高 → 该答不答 |
| `run_safety_checks.sh` | 越权类答错被放行 |
| `run_prompt_e2e.sh` | Prompt 改版后行为漂移 |

#### 4. Badcase + runs.jsonl

线上/Curl 翻车 → 录入 case → 改 Prompt/知识库/阈值 → 回归通过再发版。

#### 5. Skills A/B + Prompt 热加载

`skills/*/SKILL.md` 分桶试验；`POST /prompts/reload` 快速迭代话术，减少系统性答错。

#### 6. 产品边界

免责声明 + 「非诊断系统」：即使偶发答错，也不让用户当成医嘱——这是合规层兜底。

---

### 8.8 全链路示例

**场景 A：模型想开药（答错类型 = 越权）**

```
输入「该吃什么药」→ check_question 拦截 → blocked=true
（Agent 不被调用）
```

**场景 B：模型说了「你就是肺癌」（答错 = 确诊）**

```
Agent 生成 → Safety Judge 规则拦截
→ safety_passed=false, hitl_required=true
→ 返回 safe_response 或 Judge rewrite
```

**场景 C：模型 JSON 乱格式（答错 = 格式）**

```
ReportAgent 结构化失败 → agent_report_retry → 模板渲染成功
```

**场景 D：模型把 ALT 解释偏了（答错 = 事实，但语气正常）**

```
Judge 可能仍 passed=true
→ 依赖 sources 人工核对 + chat_eval 人工评
→ 记入 Badcase，补 ALT.md 或改 Prompt
```

---

### 8.9 设计哲学（面试可用）

> 本项目**不追求 LLM 永不答错**，而是：  
> 1. **程序能判的错**（无依据、越权、紧急、空答）→ 拦或改；  
> 2. **程序难判的错**（细粒度事实）→ sources 追溯 + HITL 信号 + 人工评测闭环；  
> 3. **指标诚实地**用 `effective_answer` / `hitl_rate` 区分「答了且安全」与「需人看」。

---

### 8.10 已知局限与可增强方向

| 局限 | 可增强 |
|------|--------|
| Judge 失败降级可能放过边缘越权 | 加强规则库、Judge 必选 |
| 无自动事实核查（answer vs sources） | RAGAS faithfulness、LLM-as-Judge 对照 sources |
| 无用户点踩在线学习 | 反馈 → Badcase 自动入库 |
| chat_eval 人工为主 | 加 BERTScore / 要点 checklist 半自动 |

---

### 8.11 面试 30 秒版

> 答错分三层处理：**预防**用 Evidence-first 和专 Agent 少错；**当场**用结构化重试、Agent Fallback、空答拒答；**事后**用 Safety Judge 拦截越权并可选 rewrite，同时返回 `safety_passed`、`hitl_required`、`sources` 供人工核对。事实性小错不靠假自检，靠 **runs.jsonl + chat_eval 人工评 + Badcase 回归** 迭代。

## 9. HITL 人工介入设计

### 9.1 定位：信号型 HITL，而非完整工单系统

本项目的 HITL **不是**「每条回答都进人工审核队列」，而是：

> **在全链路各阶段自动打上「需人工关注」信号**，并配套 **审计、指标、依据追溯**，让运营/医生/下游系统知道哪些会话不能当 AI 已闭环处理。

POC 阶段人工复核靠 **`runs.jsonl` 筛选 + `sources` 对照**；API 契约与 Prometheus 指标已为接入真实 HITL 工单（CRM、呼叫中心、医生工作台）留好钩子。

---

### 9.2 独特设计 1：分阶段、分原因打标（不是一刀切）

`hitl_required` 在 `SecurityCheckResult`（`core/medical_security.py`）里按场景精细设置，**并非所有拦截都要人工**：

| 场景 | `hitl_required` | 原因 |
|------|-----------------|------|
| 紧急症状（胸痛、窒息等） | ✅ | 必须转线下/120 |
| 开方/确诊/剂量类输入 | ✅ | 越权，需医生 |
| 敏感词 / 内容安全 API | ✅ | 合规风险 |
| 无检索依据 / 低分拒答 | ✅ | 可能需补知识或人工解释 |
| Agent 空回复 | ✅ | 链路异常 |
| 纯偏题（写代码、讲笑话） | ❌ | 直接拒答即可 |
| 空问题 / 过长 | ❌ | 用户输入问题 |

解决的是：**运营不会被「偏题拒答」淹没，HITL 队列里主要是「真有风险、真缺依据、真紧急」的 case**。

---

### 9.3 独特设计 2：三信号 `emergency` / `escalated` / `hitl_required`

API 契约（`ChatResponse` + `contracts/medical_chat_response.schema.json`）同时暴露三个布尔字段，语义分层：

| 字段 | 含义 | 典型触发 |
|------|------|----------|
| `emergency` | 急症 | 输入规则命中 → EmergencyAgent + 120 模板 |
| `escalated` | 升级 | 紧急 / Agent 自标 escalate / urgency=CRITICAL / Judge 未过 |
| `hitl_required` | 建议人工介入 | 拦截阶段用 `sec.hitl_required`；成功路径用 escalated ∨ ¬safety_passed |

**Orchestrator 侧**（`agents/agent_orchestrator.py`）综合 Intent 紧急度：

```python
escalated = (
    emergency
    or response.escalate
    or req.urgency == UrgencyLevel.CRITICAL
)
```

`EmergencyAgent` 即使「成功」返回 120 模板，也 **`escalate=True`**，不会算作普通成功对话。

**成功路径 KPI 计算**（`api/main.py`）：

```python
effective = agent_success and safety_passed
hitl = escalated or not safety_passed or emergency
```

解决的是：**前端/呼叫中心能区分「急症转 120」「安全升级」「一般拦截」，而不是只有一个 blocked 布尔值**。

---

### 9.4 独特设计 3：与「有效回答」对立的 KPI

很多项目只统计「有没有返回 200 + 有正文」。本项目刻意拆成两个对立指标：

| 指标 | Counter | 含义 |
|------|---------|------|
| 有效回答率 | `medical_chat_effective_answers_total` | Agent 成功 **且** Judge 通过 |
| 人工转接率 | `medical_chat_hitl_total` | emergency / escalated / hitl_required 等需人工关注 |

Prometheus 预聚合（`prometheus/recording_rules/medical-kpi.yml`）：

```yaml
medical:hitl_rate:5m = rate(hitl_total) / rate(chat_requests)
medical:effective_answer_rate:5m = rate(effective_answers) / rate(chat_requests)
```

`/health` 的 `audit.hitl_rate` 汇总近 500 条 `runs.jsonl`。

解决的是：**Judge 改写后仍算 HITL、紧急模板仍算 HITL，避免「看起来答了」就虚高成功率**。

---

### 9.5 独特设计 4：Judge 改写后仍标 HITL

Safety Judge 未通过时（`core/safety_judge.py`）：

1. 优先返回 Judge 的 **`rewrite`** 安全改写
2. 同时 **`safety_passed=false`、`hitl_required=true`**

用户看到的是安全话术，但系统仍标记「这条不能当 AI 闭环」，方便事后人工抽检 Judge 改写是否到位、原回答错在哪。

---

### 9.6 独特设计 5：全链路审计 = 轻量人工队列

每条 `/chat` 写 `observability.py` → `logs/runs.jsonl`，包含：

- `request_id`、`hitl_required`、`hitl_escalated`
- `outcome`（`blocked_emergency` / `blocked_judge` / `success` …）
- `response_preview`（PII 脱敏 + 截断）
- `source_count`、`intent`、`agent_type`、`effective_answer`

POC 下人工复核流程：

```
Prometheus 告警 hitl_rate 升高
  → 筛 runs.jsonl 中 hitl_escalated=true
  → 用 request_id + sources[] 对照知识库
  → 录入 Badcase → 改 Prompt/知识库/阈值 → 回归
```

解决的是：**没有独立 HITL 后台，也能跑通「发现 → 追溯 → 迭代」闭环**。

---

### 9.7 独特设计 6：HITL 与 RAG 依据绑定

需人工的 case 往往带 **`sources[]`**（title、content、score）和 `request_id`。  
事实性争议时，人不必猜模型说了什么——**直接对照引用片段**复核。

解决的是：**HITL 不是「让人从头审一整段自由文本」，而是「带依据的复核」**，降低人工成本。

---

### 9.8 解决了什么问题

| 问题 | HITL 设计如何解 |
|------|----------------|
| AI 不能当最终医嘱 | 越权/紧急/无依据 → 拒答或改写 + 强制 HITL |
| 运营不知道哪些会话要跟进 | API 信号 + `hitl_rate` 指标 + JSONL 可筛 |
| 成功率指标被「不安全回答」污染 | `effective_answer` 与 `hitl` 分开统计 |
| 急症被当成普通问答 | `emergency` + EmergencyAgent + 输入层双检 |
| Judge 改写了就万事大吉 | 改写仍 `hitl_required`，保留抽检入口 |
| POC 没有工单系统 | 契约化字段 + 审计日志，方便接 CRM/呼叫中心 |

---

### 9.9 与常见方案的差异

| 常见做法 | 本项目 |
|----------|--------|
| 只有 blocked / error | 分 `emergency` / `escalated` / `hitl_required` |
| 拦截即失败，无分级 | 偏题不 HITL，高风险才 HITL |
| 成功率 = 有回复 | 有效回答 = Agent 成功 ∧ Judge 通过 |
| HITL = 独立人工平台 | HITL = **内嵌信号 + 可观测 + 依据包**，平台可后接 |
| 改写后视为成功 | 改写后仍计 HITL |

---

### 9.10 全链路示例

**场景 A：用户问「该吃什么药」**

```
输入预检 high_risk → blocked=true, hitl_required=true
→ 计入 medical_chat_hitl_total
→ runs.jsonl: outcome=blocked_input
（偏题类 off_topic 则 hitl_required=false，不进 HITL 分子）
```

**场景 B：用户「胸口很痛喘不上气」**

```
detect_emergency → EmergencyAgent → escalate=true, emergency=true
→ blocked=true（仍返回 120 模板）
→ hitl=true, effective_answer=false
```

**场景 C：Agent 答了但 Judge 拦截**

```
Safety Judge passed=false → 返回 rewrite 或 BLOCK_HIGH_RISK
→ safety_passed=false, hitl_required=true, escalated=true
→ effective_answer=false, 仍计 hitl
```

**场景 D：正常回答 ALT 解释**

```
Agent 成功 + Judge 通过
→ effective_answer=true, hitl_required=false
→ sources[] 仍返回，供用户自助核对
```

### 9.11 已知边界与可增强方向

| 已做 | 局限 / 未做 |
|------|-------------|
| API 三信号 + JSON Schema | 无内置人工审核 UI、派单、SLA 工单 |
| Prometheus hitl_rate | 无用户点踩 → 自动入 HITL 队列 |
| runs.jsonl 可筛 | 前端仅 meta 展示「升级/紧急/安全改写」 |
| Judge 改写 + HITL | 事实性小错若 Judge 通过，不会自动 HITL |

**可增强**：CRM Webhook 订阅 `hitl_required=true`、Prometheus 告警驱动值班、医生工作台按 `request_id` 拉详情、用户反馈一键入 Badcase。

---

### 9.12 面试 30 秒版

> 我们的 HITL 不是后置人工审每条回复，而是**全链路分阶段打标**：紧急、越权、无依据、Judge 未过才标 `hitl_required`，偏题直接拒答不占人工队列。API 同时返回 `emergency`/`escalated`/`sources`/`request_id`，指标上 **`effective_answer` 与 `hitl_rate` 对立**，避免不安全回答刷成功率。Judge 即使自动改写了，仍标 HITL 供抽检；审计走 `runs.jsonl`，POC 就能筛 case 做 Badcase 闭环。

## 10. Token 成本控制设计

### 10.1 总体思路：先计量、再少调、再控长

项目把 Token 成本控制当成**工程问题**，而非只靠「Prompt 写短一点」：

```
计量（按 stage 拆账）
  → 少调 LLM（门禁短路 + 规则/template 零成本路径）
  → RAG 降本（预检 / LITE / 缓存）
  → 控上下文长度（截断 / 压缩 / Top-K）
  → 可控重试（避免无效 burn）
```

---

### 10.2 先计量：知道 Token 烧在哪

**`core/token_usage.py`** 用 ContextVar 做**请求级**累加；所有 LLM 必须走 **`core/llm_utils.create_message`**（禁止直接 `client.messages.create`）。

| 输出 | 用途 |
|------|------|
| `tokens_by_stage` | 按 stage 拆账（`rag_rewrite` / `agent_triage` / `judge` …） |
| `runs.jsonl` | 每次 `/chat` 落盘，便于查高成本 case |
| Prometheus `medical_llm_tokens_total{stage, kind}` | 大盘看哪条链路最贵 |
| `medical_chat_estimated_tokens` | 单次请求总 Token 分布 |

API 无 usage 时用 `len(text)//2` 粗估，并标 `tokens_estimated=true`。

解决的是：**不能优化看不见的东西**——先按 stage 拆账，再决定砍 RAG 还是 Agent。

---

### 10.3 少调 LLM：门禁短路（最大省 Token 手段）

完整 `/chat` 理论上有 Intent + RAG(改写+重排) + Agent + Judge，但大量请求**走不到后面**：

| 路径 | LLM 次数 | 机制 |
|------|----------|------|
| 紧急 / 越权 / 敏感 / 无依据 | **0** | 输入/RAG 门禁直接拒答 |
| 纯寒暄「你好」 | **0** | `GreetingAgent` 模板；且不触发 RAG |
| 偏题（写代码等） | **0** | 规则拦截（默认不调偏题 LLM） |
| RAG 预检未达 0.4 | **0 Agent** | 检索不过关就不生成 |

寒暄还配合 **`_requires_knowledge_evidence()`**（`api/main.py`）：非医学问题不跑改写/重排，避免无意义 RAG LLM。

解决的是：**最贵的 Agent 生成，只给「该答且有权答」的问题**——安全与成本同构。

---

### 10.4 RAG 降本：预检 + LITE + 缓存（核心亮点）

RAG 全链路 = **1 次改写 + N 次并行召回 + 1 次重排**，成本高。实现入口：`api/main.py` → `_build_knowledge_context`。

#### 1. RAG 预检（默认开，`RAG_PREFLIGHT_ENABLED=true`）

```
Top-1 向量检索
  → score < 0.4 或无命中 → 跳过 rewrite + rerank（约省 2 次 LLM）
  → score ≥ 0.4 → 才走 search_with_rewrite 全链路
```

与 Evidence-first **共用阈值 0.4**（`MIN_RETRIEVAL_SCORE`），一次预检同时服务「该不该答」和「值不值得花 Token 做改写重排」。

#### 2. RAG_LITE（省钱档，`RAG_LITE=true`）

始终**仅向量检索**，无改写/重排；仍走工具缓存，仍受 0.4 阈值约束。与预检互斥（LITE 优先）。

#### 3. 检索工具缓存

`knowledge_search` 注册 **`cache_ttl=300`**（5 分钟），相同 query 命中缓存不再打 Chroma + 不再触发 RAG LLM。

#### 4. 其他 RAG 控长细节

| 控制点 | 值 | 位置 |
|--------|-----|------|
| Chat 注入 Top-K | 3 | `_build_knowledge_context` |
| 单条片段注入 Prompt | `content[:600]` | `format_rag_context` |
| API 返回 sources | `content[:400]` | `_pack_rag_hits` |
| 重排跳过 | `len(items) <= top_k` 不调 LLM | `_rerank` |
| 索引 chunk | 500 字 | `knowledge_base._chunk_text` |
| 重排候选序列化 | 每条 `[:200]` | `_rerank` |

---

### 10.5 控上下文长度：多轮不爆炸

| 控制点 | 配置 | 作用 |
|--------|------|------|
| 用户输入 | `max_length=2000` | 防超长 prompt |
| Agent history | 最近 **5 条** | 不堆全量对话 |
| Intent 辅助 | 最近 **3 轮** | 短上下文消歧 |
| 工作记忆压缩 | **≥15 条**触发，保留 **5 条 + 摘要** | 防 lost-in-middle |
| Judge 输入 | question[:500] + response[:1500] | 审核控长 |
| 偏题 LLM | message[:500] | 可选模块控长 |

---

### 10.6 按 stage 封顶 `max_tokens`

| Stage | max_tokens |
|-------|------------|
| `rag_rewrite` / `rag_rerank` / `intent` | 256 |
| `off_topic_classify` | 128 |
| `memory_compress` | 256 |
| `judge` | 512 |
| `agent_*` | 1024 |

解决的是：**Completion Token 上限可预期**，便于估算单次 `/chat` 成本上界。

---

### 10.7 条件调用：默认不开贵的 LLM

| 模块 | 默认 | 控成本设计 |
|------|------|------------|
| 偏题 LLM 分类 | **关**（`OFF_TOPIC_LLM_ENABLED=false`） | `should_run_off_topic_llm`：仅无医疗关键词且非寒暄才调 |
| Safety Judge | 规则先检 | 规则不过直接拦；**规则过了才调 Judge LLM** |
| Intent | 规则优先 | 紧急/寒暄 **0 LLM**；同句 **内存缓存 500 条** |
| 结构化 Agent | 失败重试 | **最多 +1 次**（`agent_*_retry`），非无限重试 |

---

### 10.8 重试策略：不白烧 Token

`create_message` 重试配置（`core/llm_utils.py`）：

- `LLM_MAX_RETRIES=1`（默认最多重试 1 次）
- `LLM_TIMEOUT_S=60` + `asyncio.wait_for`
- 仅 **timeout / 429 / 5xx / 网络** 重试
- **4xx（除 429）不重试**——坏请求不反复打

JSONL 记录 `llm_retry_count`、`llm_errors[]`；Prometheus 有 `medical_llm_retries_total`。

---

### 10.9 典型一次 `/chat` 的 Token 账单

**最便宜：寒暄**

```
输入预检(规则) → GreetingAgent(模板) → 0 LLM
```

**中等：正常导诊（预检通过）**

```
预检(向量) + rewrite(256) + rerank(256) + intent(256) + agent(1024) + judge(512)
≈ 4~5 次 LLM（Intent 可能缓存命中更少）
```

**预检拦截：**

```
预检(向量) → 拒答 → 省 rewrite + rerank + agent + judge
```

**被输入/RAG 门禁拦：**

```
0 次 LLM（或仅可选偏题 LLM）
```

---

### 10.10 环境变量速查

| 变量 | 默认 | 作用 |
|------|------|------|
| `RAG_PREFLIGHT_ENABLED` | `true` | 低分跳过 rewrite/rerank |
| `RAG_LITE` | `false` | 仅向量检索，无 RAG LLM |
| `MIN_RETRIEVAL_SCORE` | `0.4` | 预检、LITE、门禁共用 |
| `LLM_MAX_RETRIES` | `1` | LLM 有界重试 |
| `LLM_RETRY_ENABLED` | `true` | 是否启用重试 |
| `LLM_TIMEOUT_S` | `60` | 单次 LLM 超时 |
| `OFF_TOPIC_LLM_ENABLED` | `false` | 偏题 LLM 分类 |

阈值标定见 `scripts/run_retrieval_eval.sh`。

---

### 10.11 解决了什么问题

| 问题 | 设计如何解 |
|------|------------|
| RAG 改写重排每问必调，成本高 | 预检低分跳过；LITE 模式；工具缓存 |
| 拒答/拦截仍调 Agent | 多层门禁短路 |
| 多轮 Token 爆炸 | 15 条压缩 + Agent 只吃 5 轮 |
| 不知道哪条链路贵 | stage 级 Token 指标 + JSONL |
| 重试雪崩 | 有界重试 + 4xx 不重试 |
| 效果与成本难权衡 | 环境变量切换预检/LITE，阈值用 retrieval eval 标定 |

---

### 10.12 已知边界与可增强方向

| 已做 | 局限 / 未做 |
|------|-------------|
| stage 级计量 + RAG 预检 | 无按租户/用户 Token 配额 |
| 门禁短路 + max_tokens 封顶 | 无动态模型路由（简单问小模型） |
| 检索工具 5 分钟缓存 | 画像 `update_profile` 后台仍消耗 Token |
| 结构化失败最多 +1 次重试 | 重试本身是质量换成本 |

**可增强**：Token 预算 middleware、按 intent 选模型、Prompt 缓存、RAG 结果 Redis 跨实例共享。

---

### 10.13 面试 30 秒版

> Token 成本分四层：**计量**上 `create_message` 统一入口，按 stage 写 Prometheus 和 runs.jsonl；**少调**上输入/RAG 门禁短路，寒暄和紧急走零 LLM 模板；**RAG 降本**上默认 Top-1 预检，低分跳过改写重排，省钱开 `RAG_LITE`，检索走 5 分钟缓存；**控长**上 top_k=3、片段 600 字、多轮 15 条压缩。效果与成本通过 `RAG_PREFLIGHT` / `RAG_LITE` 和 retrieval 阈值 eval 标定。

## 11. 回答质量提升设计

### 11.1 总体思路：质量 = 找对题 + 找好依据 + 结构化生成 + 可测迭代

项目提升「回答效果」不是靠一句 Prompt「请认真回答」，而是把质量拆成**可工程化的链路**：

```
检索质量（找对人读对书）
  → 路由质量（问挂科别走报告 Agent）
  → 生成质量（RAG + 专 Prompt + 结构化 + Skills）
  → 多轮质量（记忆 + 每轮 fresh RAG）
  → 输出质量（Safety Judge + 模板兜底）
  → 持续迭代（评测 + Badcase + 热加载）
```

与 §4「答得准、安全、有据」的关系：§4 讲主链路与三道门禁；本章聚焦**如何系统性提升生成效果**及**如何证明有效**。

---

### 11.2 检索质量：先让模型「有东西可读」

#### 1. 查询改写 + LLM 重排（`mcp/tool_manager.py`）

| 步骤 | 作用 |
|------|------|
| **rewrite** | 1 问扩成 3 个角度子 query，缓解口语 vs 文档表述不一致 |
| **并行召回** | 多 query 同时搜，合并去重 |
| **rerank** | LLM 按相关性重排，Top-K 更贴近用户意图 |

解决：**向量相似度 ≠ 对用户有用**——重排后 Agent 看到的片段更准。

#### 2. 多租户知识库 + shared 公共库

ChromaDB 按 `tenant_id = 本租户 OR shared` 过滤，减少跨租户噪音，提高命中 relevant 文档的概率。

#### 3. Evidence-first 阈值标定

`MIN_RETRIEVAL_SCORE=0.4` 用 `run_retrieval_eval.sh` 离线扫描推荐（详见 §5）——**宁可少答，也不拿弱相关片段硬答**。

#### 4. RAG 预检

Top-1 太低直接拒答，避免用垃圾 context 生成「看起来对其实错」的回答（详见 §6、§10）。

---

### 11.3 路由质量：问对题、走对 Agent

#### 1. 三信号 Intent 投票（`core/intent_recognizer.py`）

```
LLM 识别 (权重 0.7~0.85)
  + Embedding 模板匹配 (0.2)
  + 规则关键词 (0.1~0.15)
  → 加权投票 → triage / report / general / emergency / greeting
```

解决：**单一 LLM 判意图不稳定**——规则兜底紧急/寒暄，embedding 补口语变体。

#### 2. 专用 Agent + 独立 System Prompt

| Agent | 场景 | 质量收益 |
|-------|------|----------|
| TriageAgent | 挂科导诊 | 话术聚焦科室建议 |
| ReportInterpretationAgent | ALT/血糖等 | 聚焦指标解释结构 |
| GeneralMedicalAgent | 流程/科普 | 泛医学兜底 |
| GreetingAgent / EmergencyAgent | 寒暄/急症 | 固定模板，零幻觉 |

各 Agent 独立 system prompt（`prompts/agents/`），禁止确诊/开方写在规则里。

#### 3. Agent Fallback

专 Agent 失败 → 自动 Fallback General（`agent_orchestrator._execute`），避免空答或 500，保证**最低可用质量**。

---

### 11.4 生成质量：Prompt 工程 + 结构化 + Skills

#### 1. 分层 Prompt 体系（`prompts/`）

| 组件 | 文件 | 作用 |
|------|------|------|
| 系统规则 | `shared/system_rules.txt` | 角色、边界、证据引用规范、失败策略 |
| Few-shot | `shared/few_shot.txt` | 正确样例 + 无证据拒答样例 + 边界样例 |
| 注入防护 | `shared/injection_guard.txt` | 检索/记忆标为不可信数据区 |
| Agent 角色 | `agents/triage_role.txt` 等 | 各 Agent 专属职责 |
| RAG 模板 | `rag/context.yaml` | 统一 `[证据#n]` 格式 |

解决：**模型不知道医疗边界、不知道无证据该怎么答**——Few-shot 直接校准格式与拒答行为。

#### 2. 结构化 JSON + Markdown 模板渲染

```
LLM 输出 JSON（output_schemas.yaml 定义字段）
  → structured_response 校验必填字段
  → 渲染 templates/triage_response.md 等固定段落
  → 失败重试 1 次 → 仍失败回退原文
```

导诊固定：**症状理解 → 建议科室 → 就医建议**；报告固定：**指标含义 → 影响因素 → 下一步**。

解决：**自由文本结构漂移**——用户每次看到的段落一致、信息完整。

#### 3. Skills 动态注入（`skills/*/SKILL.md`）

- 按 **keywords + agent_type** 匹配（如 ALT → 报告解释规范）
- 支持 **A/B 分桶**（`experiment` / `variant` / `weight`，按 `user_id` 哈希）
- 热加载 `POST /skills/reload`
- Skill 正文与 `templates/*.md` 段落对齐，避免 JSON 字段与渲染结构不一致

解决：**运营侧快速调话术、做实验**，不必改代码发版。

#### 4. RAG 上下文注入方式

Agent `_call_llm` 采用**背景块 + 当前问题分离**（详见 §7）：

```
[不可信背景：记忆 + RAG 片段]
assistant: 已记录为待分析材料
user: 当前轮问题
```

降低把检索内容当指令、或旧对话绑死本轮的概率。

#### 5. 证据引用规范

System rules 要求引用 `[证据#n]`，RAG 模板带 title/score/source——回答可对照 `sources[]` 核验，也引导模型「贴着片段说」。

---

### 11.5 多轮质量：上下文不拖后腿

| 设计 | 质量收益 |
|------|----------|
| **每轮 fresh RAG** | 追问「挂什么科」重新检索导诊文档，不沿用上一轮 ALT 片段 |
| **三级记忆** | 工作/情景/画像融合，短追问有上文 |
| **Intent 只吃 history[-3:]** | 「那严重吗」仍能判 triage |
| **15 条压缩留 5 条+摘要** | 长会话不丢关键信息、不爆窗口 |

解决：**多轮答偏题、答旧题、中间信息丢失**（lost-in-middle）。详见 §7。

---

### 11.6 输出质量：生成后再检一遍

Safety Judge（`core/safety_judge.py`）：

- 规则：拦越权确诊、开方、敏感内容
- 可选 LLM Judge + **rewrite** 安全改写
- 规则 fail-closed；Judge LLM 失败降级但不放过规则命中

解决：**语气正常但内容越权**的「高质量幻觉」——安全维度单独一道关。详见 §4、§8。

---

### 11.7 质量闭环：可测、可改、可回归

| 手段 | 测什么「效果」 |
|------|----------------|
| `run_retrieval_eval.sh` | 检索该不该放行（影响有无好依据） |
| `run_safety_checks.sh` | 安全拒答是否正确 |
| `run_prompt_e2e.sh` | Intent、must/must_not 正则、规则 Judge |
| `run_chat_eval.sh` | 端到端 blocked/emergency/RAG + **人工读 full_response** |
| `runs.jsonl` + Badcase | 线上翻车 → 改 Prompt/知识库/Skill → 回归 |
| `POST /prompts/reload` | Prompt 热加载，快速迭代 |
| Prometheus | RAG 命中率、effective_answer_rate、Judge 拦截率 |

解决：**改 Prompt 不知道有没有变差**——分层评测，检索/安全可自动化，医学内容有人工抽检。

### 11.8 全链路示例（质量如何叠加）

**第 1 轮：「ALT 52 偏高什么意思」**

```
1. Intent 投票 → report
2. RAG 改写+重排 → 命中 ALT.md，score≈0.51 ≥ 0.4
3. ReportAgent + report_role + few_shot + RAG[证据#1]
4. Skills：报告解释规范（措辞、禁止确诊）
5. 结构化 JSON → 渲染 report_response.md
6. Safety Judge 通过
7. 返回 response + sources[]（人可核对）
```

**第 2 轮：「那要挂什么科」**

```
1. 记忆提供「上一轮在聊 ALT」
2. fresh RAG 按当前句检索导诊文档
3. Intent(history[-3:]) → triage
4. TriageAgent + 导诊 Skill + 结构化模板
```

### 11.9 设计哲学（面试可用）

> 回答质量在本项目里 = **Relevance（路由+RAG）+ Groundedness（Evidence-first）+ Format（结构化+模板）+ Safety（Judge）+ Iteration（评测闭环）**。  
> 不追求模型「更聪明」，而是让**对的 Agent、对的片段、对的格式**在对的时机组合起来；测不准的地方用拒答和 HITL 兜底，而不是硬答。

## 12. 大模型接口超时解决方案

### 12.1 总体思路：统一入口硬超时 + 可重试 + 业务降级 + 可观测

项目**不依赖** SDK 默认超时（可能无限等待），所有 LLM 调用强制走 **`core/llm_utils.create_message`**，在应用层用 `asyncio.wait_for` 做**硬超时**，再配合重试、降级和指标告警。

```
create_message（LLM_TIMEOUT_S 硬超时）
  → 超时/5xx/网络 → 有界重试 + 退避
  → 仍失败 → Agent 降级 / Judge 降级 / 友好文案
  → 指标 + runs.jsonl + 告警
```

---

### 12.2 核心机制：统一 LLM 入口 + 硬超时

实现（`core/llm_utils.py`）：

```python
resp = await asyncio.wait_for(
    client.messages.create(**kwargs),
    timeout=timeout_s,  # LLM_TIMEOUT_S，默认 60
)
```

| 环境变量 | 默认 | 作用 |
|----------|------|------|
| `LLM_TIMEOUT_S` | **60** 秒 | 单次 LLM 调用上限 |
| `LLM_MAX_RETRIES` | **1** | 超时后最多再试 1 次 |
| `LLM_RETRY_ENABLED` | `true` | 是否启用重试 |
| `LLM_RETRY_BACKOFF_S` | **0.5** | 重试前随机退避（×1~2） |

**规范**：禁止直接 `client.messages.create`；必须带 `stage`（如 `agent_triage`、`rag_rewrite`、`judge`），便于按 stage 定位超时点。

解决的是：**接口卡住拖死整个 `/chat` 协程**——到点必抛 `asyncio.TimeoutError`，不会无限挂起。

---

### 12.3 超时识别与自动重试

`classify_llm_error()` 将异常归类：

| reason | 是否可重试 |
|--------|------------|
| `timeout`（`asyncio.TimeoutError` 或异常名/文案含 timeout） | ✅ |
| `rate_limit`（429） | ✅ |
| `server_error`（5xx） | ✅ |
| `network`（连接类） | ✅ |
| `client_error`（4xx 除 429） | ❌ |

超时属于 **retryable**，在 `LLM_MAX_RETRIES` 范围内自动再调一次，并记录 `medical_llm_retries_total{stage}`。

解决的是：**偶发网络抖动或 Provider 慢响应**——一次超时不立刻给用户失败。

---

### 12.4 业务层降级：超时后用户仍有响应

单次 LLM 最终仍失败时，各层有兜底，避免 500 或无响应：

#### 1. Agent 层（`agents/agent_orchestrator.py`）

```python
except Exception:
    return AgentResponse(
        content="抱歉，暂时无法处理您的问题，请稍后重试或前往医疗机构咨询。",
        success=False,
    )
```

- `agent_success=False` → `outcome=llm_failed`（不计入有效回答）
- 专 Agent 失败 → **Fallback 到 General Agent** 再试一次

#### 2. Safety Judge 层

Judge LLM 超时/异常 → **降级为仅规则通过**（规则仍拦确诊/开方/敏感词），不因 Judge 超时打挂整请求。

#### 3. RAG 工具层（`mcp/tool_manager.py`）

知识检索 handler 单独 **`timeout_s=30`**，`asyncio.wait_for` 超时 → 走 **fallback**，不阻塞主链路。

#### 4. 偏题 LLM / 内容安全 API

- 偏题分类失败 → fail-open 放行
- `CONTENT_SAFETY_API_TIMEOUT_S=5` 短超时，避免外部 API 拖慢主链路

#### 5. 零 LLM 路径

紧急模板、寒暄模板、输入/RAG 门禁拒答——不调 LLM，不受 Provider 超时影响。

---

### 12.5 可观测：发现超时、定位 stage

#### Prometheus

| 指标 | 含义 |
|------|------|
| `medical_llm_errors_total{stage, reason="timeout"}` | 各 stage 超时次数 |
| `medical:llm_timeout_rate:5m` | 5 分钟超时率（recording rule） |
| `medical:llm_failure_rate:5m` | LLM 总体失败率 |
| `medical_chat_requests_total{outcome="llm_failed"}` | Chat 因 Agent LLM 失败 |

#### runs.jsonl

每条请求记录：

- `llm_errors[]`（含 `stage`、`reason: timeout`）
- `timeout: true`（由 `llm_errors` 推导）
- `/health` → `audit.llm_timeout_rate`

#### 告警（`prometheus/alerts/medical-diagnostics.yml`）

| 告警 | 触发 | 排查提示 |
|------|------|----------|
| `LlmErrorRateHigh` | 5m 内 LLM 错误 > 0.05/s | 查 `LLM_TIMEOUT_S`、API Key、base_url |
| `LlmFailureRateHigh` | 失败率 > 15% | 查 `medical_llm_errors_total` |
| `AgentSuccessRateLow` | `agent_success_rate < 0.85` | 查 Agent 阶段超时/失败 |

---

### 12.6 预防性设计：减少「等到超时」

| 手段 | 与超时的关系 |
|------|----------------|
| RAG 预检 / LITE | 低分跳过 rewrite+rerank，少 2 次 LLM |
| 门禁短路 | 大量请求 0 LLM |
| 各 stage `max_tokens` 封顶 | 生成更短，降低慢响应概率 |
| `normalize_anthropic_base_url` | 避免 `/v1/v1/messages` 404 反复失败 |
| Intent 缓存（500 条） | 同句不重复调 LLM |

大上下文场景可在 `.env` 将 **`LLM_TIMEOUT_S=90`** 略增，减少误杀慢请求（需与 SLA 权衡）。详见 §10。

---

### 12.7 超时层级区分

| 层级 | 超时对象 | 默认值 |
|------|----------|--------|
| **`create_message`** | 每次 LLM API 调用 | `LLM_TIMEOUT_S=60` |
| **tool_manager** | 知识检索 handler | 30s |
| **content_safety API** | 外部 HTTP | 5s |
| **eval 脚本 httpx** | 整次 `/chat` HTTP（测试用） | 120~180s |

**注意**：一次 `/chat` 可能串行多次 LLM（Intent + RAG + Agent + Judge），**每段各自 60s**，极端情况下总耗时会叠加——尚未做「整请求级 deadline」。

---

### 12.8 全链路示例

**场景 A：Report Agent 第 1 次超时，重试成功**

```
create_message(stage=agent_report) → 60s TimeoutError
  → record_llm_error(reason=timeout)
  → 退避 0.5~1s 后重试 → 第 2 次成功
  → agent_success=true, outcome=success
```

**场景 B：Agent 两次都超时**

```
agent_report 超时 ×2 → success=False
  → Fallback General → 若仍失败
  → 返回友好拒答文案
  → outcome=llm_failed, effective_answer=false
  → runs.jsonl: llm_errors=[{stage, reason:timeout}, ...]
```

**场景 C：Judge LLM 超时**

```
规则已通过 → Judge LLM 超时
  → 降级仅规则 → 请求仍可正常返回（若 Agent 成功）
```

---

### 12.9 已知边界与可增强方向

| 已做 | 未做 |
|------|------|
| 单次 LLM 硬超时 + 有界重试 | 无 SSE 流式「先出字」降低体感等待 |
| stage 级指标 + 告警 | 无 `/chat` 级总 deadline（如整请求 90s 砍断） |
| Agent 友好降级 + Fallback | 无超时自动切换备用 Provider |
| Judge/偏题 fail-open | 无超时自动跳过 Judge LLM |

**可增强**：整请求 `asyncio.wait_for` 总预算、流式输出、Provider 多活 failover、超时率驱动动态调 `LLM_TIMEOUT_S`。

---

### 12.10 面试 30 秒版

> 所有 LLM 走 `create_message`，用 `asyncio.wait_for` + `LLM_TIMEOUT_S`（默认 60s）硬超时；超时归类为 retryable，配合 `LLM_MAX_RETRIES` 和随机退避自动重试。Agent 仍失败则 Fallback General 并返回友好文案，`outcome=llm_failed`；Judge 超时降级为规则通过。Prometheus 有 `medical_llm_errors_total{reason=timeout}` 和 `llm_timeout_rate` 告警，runs.jsonl 记 `llm_errors` 便于按 stage 排查；同时用 RAG 预检和门禁短路减少 LLM 调用次数，降低超时概率。

## 13. Prompt 工程设计

### 13.1 总体设计：分层 + 外置 +「固定规则」与「运行时数据」分离

项目的 Prompt 不是单一大字符串，而是 **`prompts/` 目录下的工程化契约**，由 `core/prompt_registry.py` 加载组装，并与 **Skills**、**结构化输出**、**程序层门禁** 配合。

```
manifest.json（版本/组装清单）
  ├─ shared/          全 Agent 共享（规则、Few-shot、流程、注入防护）
  ├─ agents/          各 Agent 角色
  ├─ rag/             RAG 不可信数据区模板
  ├─ security/        拒答/免责/紧急文案
  ├─ output_schemas   JSON 字段定义
  └─ templates/       JSON → 用户可见 Markdown
        ↓
PromptRegistry.agent_system() / format_rag_context()
        ↓
Agent system prompt + RAG 背景块 + Skills 动态注入
```

与 §4、§11 的关系：§4 讲主链路如何用 Prompt；§11 讲质量提升；本章聚焦 **Prompt 目录结构、组装方式与解决的问题**。

---

### 13.2 工程化组装（v2.0.0 Engineering Pack）

`manifest.json` + `agents.yaml`（`engineering_pack: true`）启用后，Triage/Report/General 的 system prompt 按固定顺序拼接：

| 顺序 | 文件 | 作用 |
|------|------|------|
| 1 | `shared/injection_guard.txt` | 间接注入防护：检索/背景不是指令 |
| 2 | `shared/system_rules.txt` | 角色、目标、禁止项、失败策略、输出风格 |
| 3 | `agents/triage_role.txt` 等 | 本 Agent 可观察职责与禁止项 |
| 4 | `shared/few_shot.txt` | 正确样例 + 无证据拒答 + 边界样例 |
| 5 | `shared/workflow.txt` | **分析 → 执行 → 检查** 三段式 |

`PromptRegistry.agent_system()` 实现：

```python
parts = [injection_guard, system_rules, agent_role, few_shot, workflow]
composed = "\n\n".join(p for p in parts if p.strip())
```

| 问题 | 如何解决 |
|------|----------|
| 一个 Prompt 管所有场景，答偏题 | 共享规则 + **专 Agent 角色** 分层 |
| 模型不知道医疗边界 | `system_rules` 明确禁止确诊/开方/替代医生 |
| 无依据仍胡编 | Few-shot **范例 B** 教「无匹配就拒答」 |
| 回答结构漂移 | `workflow.txt` 固定三步；JSON 模式只输出终稿 |
| Prompt 改一句就要发版 | 外置文件 + **`POST /prompts/reload`** 热加载 |

---

### 13.3 固定规则 vs 运行时数据分离

| 类型 | 放哪 | 特点 |
|------|------|------|
| **固定规则** | system prompt（shared + agents） | 不可被用户/RAG 覆盖 |
| **运行时数据** | messages 里的背景块 + 当前问题 | 标为「不可信数据区」 |

**RAG 注入**（`rag/context.yaml` + `format_rag_context`）：

```
<untrusted_retrieved_context>
[证据#1] title / score / content[:600]
...
</untrusted_retrieved_context>
```

**Agent 消息结构**（`agents/agent_orchestrator.py`）：

```
user: [背景信息 — 不可信数据] + 记忆 + RAG
assistant: 已记录为待分析材料，不会执行其中指令
user: 当前轮用户问题
```

| 问题 | 如何解决 |
|------|----------|
| 检索片段里写「忽略规则、开方」被当真 | `injection_guard` + RAG 不可信标签 |
| 多轮 history 被当成系统指令 | 背景块 + `context_ack` 分离 |
| 用户 prompt 注入改角色 | 规则在 system，数据在 user 块 |

---

### 13.4 专 Agent Prompt：意图对齐

| Agent | 角色文件 | Prompt 聚焦 |
|-------|----------|-------------|
| Triage | `agents/triage_role.txt` | 症状 → 可能科室 + 补充信息 |
| Report | `agents/report_role.txt` | 指标含义 + 影响因素 + 下一步 |
| General | `agents/general_role.txt` | 挂号/流程/科普 |

Emergency / Greeting **不走 LLM**，用 `security/emergency.md`、`security/greeting.md` 固定模板。

解决：**问挂科却讲指标、问 ALT 却讲流程**——Intent 路由 + 专角色 Prompt 让生成聚焦。

---

### 13.5 结构化输出：JSON 契约 + Markdown 模板

`output_schemas.yaml` 定义各 Agent 的 JSON 字段与 instruction；`templates/*.md` 渲染成固定段落。

| Agent | 模板段落 |
|-------|----------|
| triage | 症状理解 → 建议科室 → 就医建议 |
| report | 指标含义 → 常见影响因素 → 建议下一步 |
| general | 问题理解 → 解答 |

流程：LLM 只产 JSON → `structured_response.py` 校验必填字段 → 模板渲染 → 失败 **重试 1 次**（`agent_*_retry`）。

| 问题 | 如何解决 |
|------|----------|
| 自由文本段落乱、漏项 | 必填字段 + 模板 |
| 导诊/报告格式不一致 | 各 Agent 独立 schema + template |
| JSON 格式偶发错误 | 同请求内 `_retry` + 纠正 prompt |

关闭某 Agent 结构化：在 `output_schemas.yaml` 设 `enabled: false`。

---

### 13.6 Security Prompt：拒答文案产品化

`prompts/security/*.md` 外置所有**对用户可见的拒答/免责/紧急**文案：

| 文件 | 用途 |
|------|------|
| `disclaimer.md` | 免责声明（`{{disclaimer}}` 占位符复用） |
| `block_no_evidence.md` | 无检索依据 |
| `block_high_risk.md` | 开方/确诊类 |
| `emergency.md` | 120/急诊模板 |
| `greeting.md` | 寒暄引导 |
| `sensitive_words.yaml` | 敏感词规则（配合程序层） |

启动时 `sync_templates_from_registry()` 同步到 `core/medical_security.py`。

| 问题 | 如何解决 |
|------|----------|
| 拒答话术散落在代码里难改 | 运营改 Markdown，热加载 |
| 免责不一致 | 统一 `{{disclaimer}}` 展开 |
| 紧急/拒答语气不专业 | 专门模板，不经 LLM 生成 |

**注意：** `Safety Judge` 的审核 Prompt **故意不外置**（安全相关硬编码在 `core/safety_judge.py`）。

---

### 13.7 Skills：Prompt 的可运营扩展层

`skills/*/SKILL.md` 按 **keywords + agent_type** 动态拼进 system prompt（如 ALT → 报告解释规范），支持 A/B 分桶（`experiment` / `variant` / `weight`）。

| 层级 | 职责 |
|------|------|
| **Prompt** | 稳定行为契约（角色、边界、格式） |
| **Skills** | 可热加载的领域话术/SOP，与 `templates/*.md` 段落对齐 |

解决：改话术做实验不必动核心 Prompt；A/B 可对比 variant 效果。热加载：`POST /skills/reload`。

---

### 13.8 版本、热加载与回归

| 机制 | 作用 |
|------|------|
| `manifest.json` version + `CHANGELOG.md` | Prompt 包版本可追溯 |
| `prompt_release_tag` → `runs.jsonl` | 线上 case 知道用的哪版 Prompt |
| `GET /prompts` / `POST /prompts/reload` | 查询摘要 / 不停机更新 |
| `evaluation/prompt_regression.py` | 规则层回归（角色含「禁止」、RAG 注入防护等） |
| `run_prompt_e2e.sh` | 端到端 must/must_not 校验 |

解决：Prompt 迭代「改了不知道有没有坏」——版本 + 分层回归闭环。

---

### 13.9 与程序层的关系（Prompt 不单打独斗）

Prompt 负责「模型该怎么想、怎么说」；以下由**代码硬保证**：

| 程序层 | 补 Prompt 的短板 |
|--------|------------------|
| Evidence-first 门禁 | 无依据不调 Agent |
| 输入预检 | 紧急/越权在 Prompt 前就拦 |
| Safety Judge | 输出后再检确诊/开方 |
| 结构化校验 | JSON 缺字段不直接给用户 |

**Prompt 是软约束，门禁是硬约束**，两层叠加。

---

### 13.10 设计解决了哪些问题（汇总）

| 痛点 | Prompt 设计对策 |
|------|----------------|
| 医疗幻觉 / 无依据编造 | system_rules 仅依据片段 + Few-shot 拒答样例 + RAG 证据格式 |
| 越权确诊开方 | 角色禁止项 + workflow 检查步 + security 拒答模板 |
| 注入攻击（RAG/用户） | injection_guard + 不可信数据区 + context_ack |
| 答非所问 | 专 Agent role + Intent 路由 |
| 格式不稳定 | output_schemas + templates + 结构化重试 |
| 运营改文案慢 | 外置 + reload + Skills A/B |
| 版本不可追溯 | manifest + release_tag + CHANGELOG |
| Prompt 改了不知道坏没坏 | prompt_regression + prompt_e2e |

---

### 13.11 面试 30 秒版

> Prompt 是 **v2.0.0 工程化契约**：`manifest.json` 组装 injection_guard、system_rules、专 Agent 角色、Few-shot、三段式 workflow；RAG 和记忆走**不可信数据区**，与固定 system 规则分离。生成侧 triage/report/general 用 **JSON schema + Markdown 模板** 保证结构稳定；拒答/免责/紧急走 `security/*.md` 外置模板。配合 Skills 热加载做话术 A/B，Prompt 本身支持 reload 和 release_tag 审计。程序层 Evidence-first 和 Safety Judge 做硬兜底——Prompt 管「怎么说」，门禁管「能不能说」。

## 14. 日志追踪与可观测设计

### 14.1 总体思路：三层观测 + 一条 request_id 串全链路

项目把「日志追踪」设计成 **指标看趋势、JSONL 查个案、告警抓异常**，而不是只靠 Python `logger` 打非结构化文本：

```
request_id（入口生成，贯穿全链路）
  ├─ Prometheus（实时 Counter/Histogram，按 outcome 分桶）
  ├─ logs/runs.jsonl（单次请求审计快照）
  └─ 标准 logger（异常栈 + request_id）
        ↓
/health.audit 汇总近 500 条 · Prometheus 告警 · Badcase 人工复盘
```

另有 **`PerformanceMonitor`** 周期采集 Agent/工具在线表现，形成第四层「组件健康」观测。与 §3.3 的关系：§3 概览三层观测；本章展开 **追踪 ID、JSONL 字段、排查流程与隐私设计**。

---

### 14.2 关联 ID：request_id + release_id + session_id

#### 1. request_id（请求级追踪）

- 生成：`observability.new_request_id()` → 12 位 hex UUID
- 写入：每条 `logs/runs.jsonl`
- 返回：`ChatResponse.request_id`，前端/调用方可带回
- 异常：`logger.exception("Chat 请求失败 request_id=%s", request_id)`

解决：用户反馈「刚才那题答错了」→ 用 `request_id` 在 JSONL 精确定位。

#### 2. release_id（版本级追踪）

```python
release_id = f"medical_kb@{doc_count}+{prompt_release_tag}"
# 例：medical_kb@42+med_rag_agent@2.0.0
```

知识库 import/add 或 Prompt reload 后更新；每条 JSONL 带 `release_id`。

解决：翻车时可区分 **Prompt 改版** vs **知识库变更**，而非「模型突然变差」。

#### 3. session_id（会话级）

JSONL 中 `session_id` = `conv_id`，用于多轮同一对话串联。

---

### 14.3 核心：logs/runs.jsonl 请求审计

实现：`observability.log_run()`；开关 `ENABLE_OBSERVABILITY_LOG`（默认开，`config.py`）。

**每条 `/chat` 各分支都会写**（成功、blocked、llm_failed、500 异常）：

| 字段 | 含义 |
|------|------|
| `ts` | Unix 时间戳 |
| `request_id` / `session_id` | 请求 / 会话 |
| `query` | 用户问题（**PII 脱敏** + 截断 200 字） |
| `outcome` | 见下表 |
| `blocked` / `blocked_reason` | 是否拦截及原因 |
| `intent` / `agent_type` | 路由结果 |
| `safety_passed` | Judge 是否通过 |
| `hitl_required` / `hitl_escalated` | 人工介入信号 |
| `rag_queried` / `rag_hit` / `source_count` | RAG 是否查、是否命中 |
| `effective_answer` | 是否有效回答 |
| `duration_ms` | 端到端耗时 |
| `response_preview` | 回复摘要（脱敏 + 截断，默认 500 字） |
| `release_id` | KB + Prompt 版本 |
| `estimated_tokens` / `tokens_by_stage` / `llm_errors` / `llm_retry_count` | Token 与 LLM 错误 |
| `timeout` | 是否发生 LLM 超时 |
| `exception_type` / `exception_message` | 500 异常信息 |

#### outcome 枚举（与 Prometheus 对齐）

| outcome | 含义 |
|---------|------|
| `success` | Agent 成功 + Judge 通过 |
| `blocked_input` / `blocked_rag` / `blocked_agent` | 各阶段门禁拦截 |
| `blocked_emergency` | 紧急症状 |
| `blocked_judge` | Judge 未过 |
| `llm_failed` | Agent LLM 失败（含超时） |
| `error` | 未预期异常 → 500 |

| 问题 | 如何解决 |
|------|----------|
| 线上 case 无法复盘 | 一行 JSON = 一次请求完整快照 |
| 不知拦在哪一层 | `outcome` + `blocked_reason` 分 stage |
| 日志含手机号/身份证 | `redact_pii` + 截断 |
| 日志过大 | `LOG_RESPONSE_PREVIEW_MAX=0` 可关 preview |
| Badcase 难挖 | 按 `hitl_escalated` / `outcome=llm_failed` 筛选 |

---

### 14.4 Prometheus：实时指标与大盘

`/chat` 各分支调用 `monitor/metrics.py` 的 `record_chat_*`，暴露 `GET /metrics`。

| 维度 | JSONL | Prometheus |
|------|-------|------------|
| 粒度 | 单次请求明细 | 聚合率/分布 |
| 用途 | 排查、Badcase | 大盘、告警 |
| 保留 | 本地文件 | 时序库 |

**关键指标：**

- `medical_chat_requests_total{outcome}` — 按 outcome 分桶
- `medical_chat_latency_seconds` — 延迟分布
- `medical_knowledge_gate_blocks_total{reason}` — RAG 门禁
- `medical_safety_judge_blocks_total` — Judge 拦截
- `medical_llm_errors_total{stage, reason}` — 含 timeout
- 业务 KPI：`medical:rag_hit_rate:5m`、`medical:effective_answer_rate:5m`、`medical:hitl_rate:5m`（recording rules）

解决：「整体变慢 / 拒答变多」用 Prometheus 看趋势，再用 `request_id` 下钻 JSONL。

---

### 14.5 告警与 /health 快捷视图

#### Prometheus 告警（`prometheus/alerts/medical-diagnostics.yml`）

| 告警 | 排查指向 |
|------|----------|
| `LlmErrorRateHigh` | `LLM_TIMEOUT_S`、runs.jsonl 的 `llm_errors` |
| `LlmFailureRateHigh` | `medical_llm_errors_total` vs `llm_attempts` |
| `EffectiveAnswerRateLow` | LLM、RAG、Judge |
| `RagHitRateLow` | 知识库 / embedding / Chroma |

`prometheus/README.md` 排查手册直接指向 **runs.jsonl 的 `blocked_reason` / `llm_errors`**。

#### /health 的 audit 字段

`aggregate_stats()` 汇总 **近 500 条** JSONL：

```json
{
  "blocked_rate": 0.12,
  "rag_hit_rate": 0.85,
  "effective_answer_rate": 0.72,
  "hitl_rate": 0.08,
  "llm_timeout_rate": 0.02
}
```

解决：POC 未起 Prometheus 也能快速看近期健康度。

### 14.6 Token 追踪并入审计

`log_run` 自动合并 `token_fields_for_log()`（来自请求级 ContextVar）：

- `tokens_by_stage` — 哪一步最耗 Token
- `llm_errors[]` — 哪一步 timeout/429
- `llm_retry_count` — 重试次数

与 §10、§12 联动：成本异常和超时异常都能按 stage 定位。

### 14.7 PerformanceMonitor：组件级在线监控

`monitor/performance_monitor.py` 周期拉取 Orchestrator / ToolManager 统计：

- 写 Prometheus：`agent_success_rate`、`agent_latency_ms`、`tool_success_rate`
- Z-score 滑动窗口异常检测
- 超阈值告警 + 可选 Webhook
- `GET /monitor` 返回摘要（需 readonly 鉴权）

解决：不仅看「/chat 成不成功」，还能看 **某个 Agent 或检索工具是否退化**。

### 14.8 隐私与合规设计

| 措施 | 实现 |
|------|------|
| query 脱敏 | `log_run` 前 `redact_pii()`（手机号、身份证段） |
| 回复不全量落盘 | 仅 `response_preview` 截断摘要 |

## 15. 检索、缓存、校验、兜底与监控

### 15.1 总体架构：五件事串在 /chat 主链路上

```
检索（RAG 找依据）
  → 缓存（少重复算）
  → 校验（多层门禁，不过关不放行）
  → 兜底（失败仍有可控结果）
  → 监控（知道哪一环坏了）
```

五块不是五个独立模块，而是**同一条链路的分工**。本章汇总实现入口与解决的问题；细节分别见 §5–§6（检索）、§10（缓存降本）、§4/§8（校验）、§12/§14（兜底与监控）。

---

### 15.2 检索（Retrieval）

#### 1. 向量检索 + 多租户（`mcp/knowledge_base.py`）

```
用户 query → ChromaDB 向量召回（top_k）
           → where: tenant_id = 本租户 OR shared
           → score = 1 - distance
```

- 文档 **500 字切块**入库
- 旧数据可 `backfill_tenant_shared` 补 tenant

| 问题 | 如何解决 |
|------|----------|
| 跨租户噪音 | tenant where + 结果二次过滤 |
| 片段粒度不当 | 500 字 chunk |

#### 2. 查询改写 + 并行召回 + LLM 重排（`mcp/tool_manager.search_with_rewrite`）

```
原始 query → LLM 扩 3 条子 query → 并行 knowledge_search → MD5 去重 → LLM rerank → Top-K
```

| 问题 | 如何解决 |
|------|----------|
| 召回不全 | 多角度 query 改写 |
| 向量分高但对用户无用 | LLM 重排 |

#### 3. RAG 预检 / LITE（`api/main.py` → `_build_knowledge_context`）

| 模式 | 行为 |
|------|------|
| **预检（默认）** | Top-1 向量预检；< 0.4 跳过 rewrite/rerank |
| **LITE** | 始终仅向量检索，无 RAG LLM |
| **全量** | 预检通过才走 rewrite + rerank |

| 问题 | 如何解决 |
|------|----------|
| 低分仍改写重排浪费且可能抬高弱相关分 | 预检短路 |
| 省钱 | `RAG_LITE=true` |

#### 4. Evidence-first 知识门禁（`check_knowledge_gate`）

需要依据的问题：`source_count=0` 或 Top-1 < **0.4** → **不调 Agent**。

解决：**无依据仍生成**（医疗幻觉）——检索与生成硬绑定。

#### 5. 注入 Agent 的格式（`format_rag_context`）

Top-3 片段、每条 `content[:600]`、统一 `[证据#n]` 格式。

解决：上下文过长、证据不可追溯。

---

### 15.3 缓存（Cache）

#### 1. 检索工具 TTL 缓存（`MCPToolManager`）

- `knowledge_search` 注册 **`cache_ttl=300`**（5 分钟）
- Key = 工具名 + params MD5 + `rerank_top_k`
- 超过 **5000** 条 LRU 淘汰 1250 条
- 缓存**最终返回结果**（含重排后），避免命中未重排原始序

| 问题 | 如何解决 |
|------|----------|
| 相同 query 重复打 Chroma + RAG LLM | TTL 命中直接返回 |
| 延迟与 Token 双高 | 5 分钟窗口内复用 |

#### 2. Intent 内存缓存（`IntentRecognizer`）

同一句（归一化前 200 字）命中缓存，最多 **500** 条，满则删一半。

解决：重复问法反复调 Intent LLM。

#### 3. 与预检配合

预检低分直接拒答 → 既不生成也不走无意义全链路。

---

### 15.4 校验（Validation）

多层校验，**按顺序短路**：

| 层级 | 实现 | 校验什么 |
|------|------|----------|
| **API 入参** | Pydantic `ChatRequest` | message 1~2000 字 |
| **鉴权** | JWT/API Key + `validate_client_user_id` | 谁能调、user_id 一致 |
| **输入预检** | `check_question` / `check_question_async` | 紧急/越权/偏题/敏感词 |
| **RAG 门禁** | `check_knowledge_gate` | 是否有合格检索依据 |
| **工具参数** | `_validate_params` JSON Schema | query 等必填、类型 |
| **结构化输出** | `structured_response` 必填字段 | JSON 缺字段不渲染 |
| **空答拦截** | `check_empty_agent_response` | Agent 正文过短拒答 |
| **输出后检** | `SafetyJudge` 规则 + 可选 LLM | 确诊/开方/敏感 |

| 问题 | 哪层拦 |
|------|--------|
| 开方/确诊类输入 | 输入预检 |
| 无库仍胡编 | RAG 门禁 |
| 恶意/畸形工具参数 | Schema 校验 |
| 格式乱/漏字段 | 结构化校验 + 重试 1 次 |
| 越权输出 | Safety Judge |
| 跨租户越权读库 | Chroma where + 结果过滤 |

---

### 15.5 兜底（Fallback / Degrade）

失败时**不 500、不空响应、不 silent fail**：

#### 1. 工具层（`MCPToolManager`）

```
调用链：缓存 → 熔断检查 → 校验 → 执行(30s超时) → 重排 → 写缓存

失败路径：
  熔断 OPEN（连续 5 次失败，60s 恢复）→ fallback
  超时/异常 → fallback + 熔断计数
  rewrite 失败 → 仅用原始 query
  rerank 失败 → 返回原始顺序 Top-K
  tool_manager 失败 → api 直接 _kb.search() 直连 Chroma
```

#### 2. Agent 层

- 专 Agent 异常 → **Fallback GeneralMedicalAgent**
- 仍失败 → 固定友好文案，`agent_success=False`，`outcome=llm_failed`

#### 3. Safety Judge 层

Judge LLM 超时/JSON 失败 → **降级为仅规则通过**（规则仍拦越权）。

#### 4. 零 LLM 兜底

紧急/寒暄/拒答走 `security/*.md` **固定模板**。

#### 5. LLM 调用层

`create_message`：timeout/429/5xx → 有界重试 1 次 + 退避（§12）。

| 问题 | 兜底方式 |
|------|----------|
| 检索工具挂掉 | fallback + 直连 Chroma + 熔断 |
| 改写/重排偶发失败 | 原始 query / 原始顺序 |
| 专 Agent 单点失败 | General Fallback |
| Judge 不可用 | 规则降级 |
| 紧急场景 | 120 模板，零 LLM |

---

### 15.6 监控（Monitoring）

#### 1. 请求级：runs.jsonl（§14）

每条 `/chat`：`request_id`、`outcome`、`blocked_reason`、RAG 命中、Token、llm_errors、release_id`。

解决：个案复盘、Badcase 挖掘。

#### 2. 聚合级：Prometheus（`monitor/metrics.py`）

| 指标族 | 看什么 |
|--------|--------|
| `medical_chat_requests_total{outcome}` | 成功/各阶段 blocked/llm_failed |
| `medical_knowledge_gate_blocks_total{reason}` | RAG 门禁原因 |
| `medical_safety_judge_blocks_total` | Judge 拦截 |
| `medical_llm_errors_total{stage,reason}` | 含 timeout |
| `medical_rag_empty_results_total` | 需要证据但 0 结果 |
| 业务 KPI | rag_hit_rate、effective_answer_rate、hitl_rate |

Recording rules + Alertmanager（`LlmErrorRateHigh`、`RagHitRateLow` 等）。

解决：系统性退化先于用户投诉被发现。

#### 3. 组件级：PerformanceMonitor + ToolStats

- Agent/Tool **成功率、延迟、连续失败**
- 熔断状态 `circuit_state`（closed/open/half_open）
- Z-score 异常检测 + 可选 Webhook
- `GET /monitor`、`GET /health.audit`

解决：区分「/chat 失败」vs **knowledge_search 工具熔断**。

---

### 15.7 五块协同：全链路示例

**「ALT 52 偏高什么意思」**

```
检索：预检通过 → rewrite+rerank → 命中 ALT.md（或缓存命中）
校验：输入放行 → RAG 门禁 score≥0.4 → 结构化 JSON → Judge 通过
```
